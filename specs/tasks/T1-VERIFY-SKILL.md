# T1-VERIFY-SKILL

## Deliverable
Implements spec R4, R5 and, for this card's docs, R21 (`specs/review-verification.md`), order-of-work item 2 of `plans/review-verification.md`. T1-VERIFY-FAULT-POINTS produces the check (`tests/scenarios/fault-points.test.ts`: each covered card-run command failed at every store write and journal append in turn, recovered with the next step, invariants checked, plus a broken-order self-test). This card wraps it for the next agent, following the cursor `create-formal-verification-skill` and `maintain-formal-verification-skill` criteria.

1. `.claude/skills/verify-card-run-writes/SKILL.md` (new, repository-only, ASCII, at most 8000 bytes). Front matter: `name: verify-card-run-writes` and a `description:` naming the card-run write protocol (the `CardRunner` store writes and journal appends) and when to use it: a change touches a covered file, a card that changes one is about to SHIP or CLOSE, the fault-point test fails, or a covered command gains a write. Without front matter the skill never registers. No placeholders: every command names real paths and the real sync commit. Sections:
   - `## Property`: a `Property:` line and a `Harm:` line, one plain sentence each (for example: after any single failed write and the next step, the stored card run and the goal journal agree; harm: a card that the journal reports in one state while the run record holds another, so the loop repeats or skips a ship, a review or an attempt).
   - `## Coverage`: one line per file, `` - `path`: `Function`, `Class.method` ``, naming what the check drives and fails, read from `fault-points.test.ts` at PREPARE: at least that test, `src/loop/card-runner.ts` (each covered `CardRunner` command), `src/state/goal-store.ts` (the store writes the test fails) and `src/state/journal.ts` (`append`). One line `` Sync commit: `<40-hex sha>` ``.
   - `## Run`: the one command `node --test tests/scenarios/fault-points.test.ts` in a fenced block and its runtime in seconds measured at the sync commit.
   - `## Bounds and assumptions`: one fault per run, at each write index of the command as counted by a first clean pass, then one recovery step; store writes atomic (temp file and rename in `src/state/store.ts`), a failed write throws and changes nothing; fixed clock; git, gh and reviewers scripted (`scriptedRunner`, `DryRunShipPath`).
   - `## Not covered`: two-session lease and review-queue interleavings, more than one fault per run, a crash inside a single write, and each card-run command the check does not drive, by name.
   - `## Shown failing`: the real-code break (R10) as file, function and the two statements swapped (a store write and the journal append that reports it), and a fenced excerpt of the failing output from `node --test --test-reporter=tap tests/scenarios/fault-points.test.ts` (the `not ok` line and the assertion message). The broken-order self-test proves the enumerator can fail; this section proves the check fails on the real code.
   - `## Bug or modelling error`: replay the counterexample against the real code step by step; if a step cannot happen in the code (a write the code never makes, an order the code never uses), the check is wrong and is corrected; if every step can happen, it is a bug.
   - `## Findings`: report a bug as a short numbered sequence of steps in the code's words (command, write that failed, stored run and journal after it, next step, invariant broken) and open a T0-bugfix card with it; never weaken the property or the model to pass; never change product code from the skill.
   - `## Extending the check`: when a covered command gains, loses or reorders a write, update the enumerator's expected writes and invariants in `fault-points.test.ts`, show the new write failing once, update the coverage record, then move the sync commit.
   - `## Keeping in sync`: tell whether a change touches covered code (`git diff --name-only` against the sync commit, intersected with the coverage record), then one of four outcomes: in sync (covered files unchanged, or changed without a write change, and the check passes: the sync commit may move), updated (the check and the record were changed to match the code, then the sync commit moves), bug (the check fails on the real code: Findings), blocked (the check cannot be brought in line without a decision: stop and ask). The sync commit moves only after confirming that the check describes the code at the new commit, and only to a commit on main, since a squash merge drops branch commits.
