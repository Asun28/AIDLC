# T0-REGISTRY-PER-CALL

## Deliverable
Each outermost `GoalController` call of `next`, `report` or `createGoal` retains at most one successfully returned card registry: the first site that needs it loads it, every later site of the same call (the `next` and the board writes a `report` runs included) uses it, a failed load is not kept, and the registry is dropped when the call returns or throws. `aidlc board` makes one loader call on its board path. The CLI card commands keep their loads. docs/ARCHITECTURE.md and docs/OPERATIONS.md state the rule in one sentence each.

## Why
Audit item F22, analysed by two consultants and ruled by the coordinator on 2026-11-12; the draft was reviewed by Codex and amended to the coordinator's rulings. On main one `aidlc report --result cards-projected` ending in `run-card` makes four loads (five when the arc stops), and `aidlc goal new`, an arc-completing `aidlc next` and `aidlc board` two each; the audit measured 750 to 940 ms per load for 294 cards. Counts below describe the exact acceptance fixtures, with open admission deadlines and successful I/O. Transition, validation, rendering and persistence rules stay unchanged. Later sites reuse the first successful registry instead of repeating I/O; changes or failures observable only through an omitted read are not observed.

## What one registry per call keeps
With the built-in dependencies, and with board outputs disjoint from the parsed card inputs (the cards directory, the archive directory and any path alias of either), no code reached from one call of `next`, `report` or `createGoal` writes a card file. The controller's own file writes are the board file under the state directory (src/loop/controller.ts:905) and the board mirror (:909); `boardMirror` accepts any path (:66-67), and the CLI sets it to `<main checkout>/_local/aidlc-board.md` (src/cli/main.ts:81). Its other writes go to the state directory: goal records, card-run records under `<state>/cards/<goalId>/` (JSON run records, not card files) and release attempts through `GoalStore` (src/state/goal-store.ts:39, :86, :98), journal appends, and lease updates. The release runner it builds at CHECKPOINT only computes the packet ("no save, no journal event, no operation", src/loop/release-runner.ts:120-121), and `ReviewQueue.pool` only reads (src/coordination/review-queue.ts:83-85). The task-card writers in src are `writeMergedStatus` of `card close --metadata` (src/loop/card-runner.ts:3200-3206) and `aidlc cards project --write` (src/cli/main.ts:796); `initProject` writes `<cardsDir>/_TEMPLATE.md` (src/scaffold/init.ts:149), which the loader skips (names that start with `_`, src/artifacts/card.ts:230); controller.ts imports none of these modules. A board mirror configured inside the parsed card inputs would be read as a file that fails to parse, an entry of `registry.errors` (card.ts:233-235), which no loader site reads (they read `registry.cards`).
