# T1-SHIP-PUBLISH

## Deliverable
The contract and the `github` implementation of a publish step: after a clean secret scan of the candidate range, push that commit and open a draft pull request, without any other part of the ship; with no scan command, push nothing. And the one change `ship` needs for it: a draft pull request is marked ready after the CI gate passes and before the merge. No caller yet.

## Why
Intent `intent/execution-gate.md`, proposed outcome 3, owner decision of 2026-11-16: the pull request opens as a draft when R3 is requested, so CI runs while R3 reviews. Today the `github` ship path reads the R3 verdict (github-ship.ts:299) before the push (:354) and the CI gate (:367-403), and CI took 14 to 22 minutes on each of the last 21 pull-request runs. Spec `specs/execution-gate.md` R5, R6 and R9. This card freezes the interface; T1-SHIP-PUBLISH-WIRE calls it.

Owner decision of 2026-11-17 (approval of the reviewed plan): the early push happens only when a local secret-scan command is configured and exits 0 on the exact candidate range, with a receipt bound to the candidate and the range; with no scan configured the push stays after the R3 pass. `publish` therefore refuses before any command without a scan command, calls `scanCandidate` of T1-SHIP-SCAN after its pull request checks, pushes the commit the receipt names, and returns the receipt as `scan` for T1-SHIP-PUBLISH-WIRE to store.

`publish` checks the pull request before it scans and pushes, as `ship` does (:313-340), so it never pushes to a branch whose pull request is merged or closed. GitHub does not merge a draft, so `ship` marks it ready, and only after `[CI-GATE-PASS]`: the R3 verdict is still read at the start of `ship`, before any of this.
