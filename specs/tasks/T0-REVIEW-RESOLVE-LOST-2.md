# T0-REVIEW-RESOLVE-LOST-2

## Deliverable
`aidlc review resolve <key> (--verdict <file> | --no-result) --reason <text>` settles a review request in the `lost` state through `ReviewQueue.resolveLost`: a verdict document the lookup found completes it, `--no-result` requeues it in its place, and either frees the pool slot of the request's stored key. Each existing requester goal journals a NOTE inside the queue's section before the queue is written; `resolveLost` frees the slot before it writes the request, so a failed journal read or append leaves the request and its pool as they were, a failed queue write leaves the request `lost`, and running the command again finishes it. Every other state and every malformed call is refused with no write. The command settles the queue request only.

## Why
Audit item F9, analysed by two consultants and ruled by the coordinator on 2026-11-12; draft reviewed by Codex and amended to the coordinator's rulings, refreshed against main at ec4f3323 after its two dependencies merged, and amended again to the planner's rulings on a Codex review of the refreshed card. A scaffold ship that times out as a whole marks its review request `lost`; the request keeps its pool slot, so a pool of one slot stays busy for every card and goal, `aidlc review release` refuses it by design, and `resolveLost`, the queue's method for it, has no caller. Editing `.aidlc/review-queue/` by hand, which CLAUDE.md forbids, was the only way out.

History: this card replaces T0-REVIEW-RESOLVE-LOST. Its requirement text differs from the predecessor's registered text in R4 (a ship joins the requeued request by the `shortKey` of its request key; the conditions under which an admission cancels it at its deadline), R8 and the Setup sentence (with `-C` a fully qualified value is normalized lexically), R9, paragraph S and entry C (those sentences, and that running the command again finishes it once the cause of the failure is gone), and Acceptance detail 2, 11 and 13 (the rows for them).
