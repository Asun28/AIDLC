# Architecture

aidlc is a library plus CLI. The library holds pure decision engines (state machines and
policies over persisted facts), a small durable state layer, coordination primitives for
multiple sessions, probes and adapters for real project tools, and the artifact chain of the
Anthropic playbook. The CLI exposes one typed directive per call and commits results.

## Module map

`src/loop/run-driver.ts` dispatches controller directives to a command-capable provider and rereads persisted state. It treats a saved reset on the goal review pool as a hold for any waiting card, even without a queue request; other pools require a current-candidate request. One runner per goal is supported at a time. The CLI binds the worker to the absolute state root and the driver's resolved session identity, and sets an execution-scoped no-ship flag. `CardRunner` refuses native shipping before merge intent or adapter invocation when that flag is set; ordinary operator commands retain shipping. The flag is a trusted-worker command guard, not a hostile-code sandbox.

`src/core/` holds the decision engines. `types.ts` defines every persisted record as a zod schema (Goal, CardRun, ReleaseAttempt, JournalEvent, Lease, ReviewRequest, OperationRecord, AuthorizationRecord, EffortEpisode) plus the constants for limits. `router.ts` classifies a request into size, kind, delivery target and modules. `deadlines.ts` computes goal/card admission deadlines and the reconciliation grace. `stop.ts` builds STOP records (`makeStop`, whose `global` defaults to true for `auth`, `audit`, `cancelled`, `ownership`, `risk`, `frozen` and `time`), the next action of a stop nothing lifts (`toolStopNextAction`) and their one-line rendering (`formatStop`). `effort.ts` bounds implementation attempts (MA2). Build directives name an attempt by `ladderNumber`, the records before it that are not `not-counted` plus one; the stored attempt numbers and the journal's numbering are unchanged (card T0-ATTEMPT-NUMBER). `review-effort.ts` selects the effort level an R3 reviewer's `{effort}` placeholder expands to from the candidate's changed lines and paths. `review-policy.ts` parses scaffold verdicts, classifies them, keeps the R3 decision ledger (two decisions, up to four for a command reviewer's repairs; `repeatedFindings` names the re-raise of a disputed finding that stops) and the finding bookkeeping (ids, `re:F<n>` re-raises, dispositions, the same-candidate rule, deadlocks, the `(class: <slug>)` defect class and `blockClasses`, the class list a formal repair directive appends). `continuation.ts` holds the pure rule of a continuation of a review stop (card T1-CONTINUE-CORE), described under Ship path adapters. `parse-guard.ts` holds the control decisions read from process output: `nulList` splits a `-z` name listing on NUL only, and `detectQuotaHold` decides a quota hold from a provider's numeric error status first, else from one word rule, and names the path that decided. `limit-reset.ts` reads the reset time a CLI limit message names (`resets 1pm (Pacific/Auckland)`) as a delay from a clock the caller passes; `finalizeReview` uses it for a quota hold that names no `retry after` delay. `iana-zones.ts` holds the zone and link names of tzdata 2026a, the only zone names `limit-reset.ts` reads. `ci-policy.ts` classifies CI failures and allows one persisted transient rerun. `health.ts` evaluates PASS/BREACH/INSUFFICIENT_DATA. `authorization.ts` binds approvals to candidate, environment and effects. `arc.ts` picks the next wave of cards; a `depends_on` id outside the goal's projection is satisfied only by the outcome the caller vouches for, which `GoalController.cardOutcomes` derives from the card registry's merged status (the rule `computeRevision` applies when it admits such a projection), and is itself never ordered, dispatched or reported. `goal-machine.ts`, `card-machine.ts` and `release-machine.ts` are the three state machines. `migrate.ts` detects data impact and builds the expand/deploy/backfill/verify/contract graph. `amendments.ts` routes live requirement changes. `roles.ts` resolves model/effort profiles per role (Claude defaults: `claude-opus-5-5` for planner, implementer, reviewer and release-specialist, `claude-sonnet-5-5` for the investigator; the Claude effort ladder in `effort.ts` is low, medium, high, xhigh, max).

`src/state/` is persistence. `paths.ts` resolves the canonical state directory (`<git common dir>/../.aidlc`, override `AIDLC_STATE_DIR`); its `git rev-parse` has 120 seconds to exit, after which the lookup throws; the hook entry's early asynchronous lookup (`prefetchRepoIdentity`) is ended at the same bound and gives no answer, so the synchronous lookup runs. `store.ts` writes JSON atomically (temp file + rename, interrupted-write detection) and owns the one read-modify-write, `updateJson`: an exclusive lock file per record (`<file>.lock`, naming its process) with an ownership-checked write and release, the deadline checked before every retry acquisition, no lock removed but by the writer that created it (a lock whose owner process is gone is refused with the file and the process id named), a lock read or removal failure after the change never replacing the change's result or error, no write when the change throws or returns the record unchanged, and a `within` section that holds another lock until the write lands; `goal-store.ts` runs every card-run write through it (`updateCardRun`; `saveCardRun` is a compare-and-set on `CardRun.revision`, bumped by every write under the lock, so a snapshot read before another write landed is refused whatever it changes, with the ledger entry named when one is missing, un-decided, resurrected or regressed) and `lease.ts` every lease write. Every goal write goes through it too (`GoalStore.updateGoal`, which counts `Goal.writes`, card T1-GOAL-UPDATE): `saveGoal` is refused with `GOAL_STALE` when another write landed since its snapshot was read, `GoalController` decides an owner's act on the record read inside the section, with its journal appends, where a write that is not a re-admission stores the events it owes in `Goal.journalOwed` and appends them after it with their key as `eventKey`, a re-admission (a resume, an extension of a time stop, a ruling, a continuation) appends its events before it and none the journal holds since the last `GOAL_STOPPED` or `GOAL_DONE`, and an owed event the journal does not hold is appended with `completed` true by the next goal command that writes the goal, or by `next`; a command whose append or record write fails exits non-zero, and is recovered by `next` once its change is in the record or when it was `next` itself (also when a derived write of its own `next` failed), else by the same command with the same input, which leaves the record and the goal events of the command run once, followed by that `next` when it is the recovery (card T1-GOAL-OWED), and a command that does not get the lock is refused with `LOCKED` and leaves record and journal as they were. Nested sections take the goal lease lock, the goal record lock, the card-run lock, the card lease lock and the journal lock in that order, and no registry loader runs inside the goal record lock. `journal.ts` is the append-only hash-chained event log and the process actor identity; `Journal.append` reads the head and appends in one `updateJson` section of the journal lock (`<goalId>.jsonl.append.lock`, record path `<goalId>.jsonl.append`, never written), which is the innermost lock: an append takes no other lock while it holds it, a caller holding the goal record, the card-run, a lease, the review-queue or the manifest lock takes that lock first, and an append reached from inside another append waits and is refused with `LOCKED` (card T0-JOURNAL-APPEND-LOCK); the session id comes from `AIDLC_SESSION`, then the Claude Code session (`CLAUDE_CODE_SESSION_ID`, exported to Claude Code's subprocesses), then a per-repository default token in `.aidlc/session-default` (single-controller interim mode); a hook process takes it from the hook event's `session_id` (`hooks/index.ts`). An identity change rewrites no lease record: a lease claimed under the default token by an earlier version, or by a Claude Code session that has ended (a `/clear` starts a new one), stays as recorded and expires after its TTL; `aidlc goal takeover` then takes the goal lease after the old owner's operations are reconciled. The session that closes the goal does the same before it saves DONE (`GoalController.nextInClose`), and saves DONE under the goal lease lock, in the section that leaves an absent or released lease as it is or in the release section right after the release write lands, through the `within` hook `LeaseStore.update` passes to `updateJson` (card T0-TAKEOVER-DONE-RACE, issue 387); both takeovers decide DONE inside a goal lease section, so a DONE saved by a close is seen by every takeover whose section runs after it. The lease steps run in two lease sections that judge the locked record: the takeover journals a handoff intent before the lease write, and the release journals `GOAL_TAKEOVER` from that intent when it is still missing, as does the takeover for the lease it replaces, so a goal finished by a session other than the intake session reaches DONE with its board and `done` directive, and a close interrupted between the two is completed by the next call, of the same session or a later one. A card lease held by an ended session is continued while it is live by a process running with `AIDLC_SESSION` set to the owner session id, which `aidlc card status` prints from the lease record, provided the run's `ownerGeneration` equals the lease generation (the renewal in `loop/card-runner.ts` requires it; a run interrupted between the lease claim and the PREPARE save has none), and `card next` from another session under that live lease returns a stop naming the holder and writes nothing. Once it has expired, `aidlc card takeover` (`CardRunner.takeover`) takes it after the card's operations in every goal are reconciled, in one lease section (`LeaseStore.update`) that checks the lease record and the operation ledger, journals the handoff intent and writes the lease, the lock a ship's fence, duplicate check and operation intent take too: the generation advances and the old owner is fenced; then, under the card-run lock and the lease lock inside it, both held until the run record is on disk, the run records the new generation (the run without one included) and one `LEASE_ACQUIRED` per generation is journaled, only while the lease is still this session's acquisition and the locked run does not carry the generation yet, so a stop saved meanwhile stays; its state is selected again through the evidence gathering `next` shares with it, which reads the stored run and never a caller's snapshot (a stale dispatch writes nothing back and a persisted blocking stop stands), and whose renewal revalidates the ownership stop; a missing or released lease, a lease this session holds at the run's generation, a live lease of another session and an unresolved operation refuse it before any write; the handoff intent (`NOTE`, `card-takeover-intent`) and the acquisition are resolved by resource and generation across every goal's journal, so a lease this session holds at a generation the run does not carry is an interrupted takeover the command completes, naming the previous owner from the intent. `next` reads the stored run before its plan-checkpoint guard as well, and lifts an ownership stop whose lease is absent or released (never one merely expired) so the claim is reachable; `recordAttempt` saves onto the stored run too but applies no fence; the handoff intent is bound to the acquiring session and the acquisition time the lease carries, and an acquisition PREPARE journaled counts as the one. Lock order is the card-run lock, then the lease lock: no card-run lock is taken inside a lease section, and neither lock is reentrant; `docs/OPERATIONS.md` (Sessions) states what stays unfenced and the windows that remain. The goal lease lock comes before both: `aidlc card takeover` runs `CardRunner.takeover`, with its card-run and card lease sections, inside a goal lease section that writes no goal lease (card T0-TAKEOVER-DONE-RACE), so the lease section of the sentence before is a card lease section, and no goal lease lock is taken inside a card-run or card lease section. `goal-store.ts` persists goals, card runs and release attempts. `claims.ts` derives, from the goal records alone, which non-terminal goal claims each planning file on the main checkout (its intent, the spec and plan of the intent's slug, its plan reference, the card file of every card it lists or its plan's task split names; the older goal keeps a path two goals claim) and selects the uncommitted ones from a `git status` of the main checkout; `aidlc doctor` (`workingTree`) prints them with the claiming goal's lease state and the Stop hook asks the session holding a goal's lease to commit that goal's files (no claims file, no second lock: the goal lease is the owner). `bounds.ts` backs `aidlc bounds`: it counts each loop bound that fired from the goal and card-run records, reading each file on its own with no snapshot across files and writing nothing, with the current outcome of the goal that hit it; a time STOP that `aidlc goal extend` lifted is not counted. `board.ts` renders the Markdown board, which is a view, never a store; its Arc line reports the arc the controller decided, so the caller hands it the outcomes it resolved (`prerequisitesClosedElsewhere`) and `aidlc board` prints the one text it writes rather than a second render of its own. `readWatch` and `renderWatch` back `aidlc board --watch`: each tick reads the goal, its card runs, the goal and card leases and the registry ids through read-only accessors, turns a read failure into its store error code on that row, and renders a screen whose record text passes one encoding point (a plain identifier as is, anything else as `asciiJson`); the watch never calls `next`, the controller, `currentActor` or the journal, and writes nothing (`docs/OPERATIONS.md`, Watching a goal).

`src/coordination/` is package S of the plan. `lease.ts` provides atomic claims with generations, heartbeat, release, takeover-after-reconciliation (exposed as `aidlc goal takeover` and `aidlc card takeover`) and fencing. `review-queue.ts` is the shared provider/account admission queue. A card-run command whose `REVIEW_ADMITTED` append fails after the queue admitted its request cancels that request, freeing the slot (card T0-REVIEW-ADMIT-STRAND). `ReviewQueue.admit` with a request key admits only that request, and only once fewer requests are ahead of it than the pool has free slots, which is how the card runner asks (card T0-REVIEW-ADMIT-FOREIGN). `reconcile.ts` is the operation ledger: intent before issue, reconciliation by provider lookup, explicit UNKNOWN. The card runner's ship continues under an `intended` merge intent that an earlier failed ship of the same candidate left, instead of recording a second one (card T0-OP-INTENT-DUP).

The release runner matches a release step's ledger records by goal and the exact idempotency key `<attemptId>:<step>:<candidateDigest>` alone, reads them and records the step's intent only when there is none in one section of the environment lease lock, and takes the last terminal match as the step instead of issuing it again (card T0-RELEASE-OP-REISSUE).

`src/probes/` gathers evidence. `exec.ts` runs commands and returns receipts (exit, output digest, timing), the async runner ending a timed-out command's whole process tree and `runSync` with `killTree` running the command under `exec-tree-helper.ts`, which applies that tree kill, with a scripted runner for tests. `git.ts` reads worktrees, HEAD, status, base resolution, divergence and containment. `base-sync.ts` compares the local base branch with `origin/<base>` for `aidlc doctor`, reading refs only and never fetching. `gh.ts` resolves PR identity, run views and check runs with pagination. Its `issuesWithLabel` (card T1-REVIEW-FOLLOWUP-CORE) reads the issues of a label, open and closed, through the REST list `repos/<repo>/issues?labels=<label>&state=all&per_page=100&page=<n>`, the label percent-encoded, from page 1 until a page with fewer than 100 entries, pull requests counted, and returns the number and the body of every entry that is not a pull request, in the order read, with the empty string for a null body; it reads REST because `gh issue list --label` is a search query of GitHub, and it throws rather than return a partial list when a call fails or times out, when the output of a page is malformed, or when 1,000 pages in a row hold 100 entries. `hook-wiring.ts` gives `aidlc doctor` its `hookCommand` line (`hookWiringReport`): whether the file that the hook dispatcher in `.claude/settings.json` or in `.claude/settings.local.json` starts exists, checked without starting a process. `toolchain.ts` gives `aidlc doctor` its `git`, `gh` and `pwsh` lines (`toolchainReport`): each version probe runs through the async runner with a 120-second bound and reads `unknown` when it reaches it. `virtualenv.ts` gives the DoD call (`dodCall`) its Python virtualenv (`virtualenvFor`, card T0-DOD-VENV): in each root in order, `.venv` and then `venv`, the first that holds the regular file `pyvenv.cfg` and its scripts directory (`Scripts` on Windows, `bin` elsewhere), and a copy of the environment with that scripts directory first on `PATH`, `VIRTUAL_ENV` set and `PYTHONHOME` removed; on Windows each variable keeps one key, spelled as the environment first spells it. The roots are the card worktree and then the main checkout for the loop-run DoD of `aidlc card attempt --outcome success`, and the card worktree only for `aidlc card mutants`. The `loopDod` record of a DoD that ran with a virtualenv names its directory in the optional field `virtualenv`; a record without one, or written before the card, has no `virtualenv` and parses as before. `processes.ts` gives `aidlc doctor` its `strayProcesses` line (`strayProcessesReport`): one bounded process listing, Windows PowerShell `Get-CimInstance Win32_Process` on Windows and `ps` elsewhere, and the processes under the main checkout or the card worktree root whose age (from the listed start time and doctor's clock on Windows, from the elapsed time `ps` reports elsewhere) is at least 30 minutes and whose cumulative CPU time is at least half of that age, printed without their arguments.

`src/delivery/` touches the project. `worktree.ts` decides start vs attach vs stop from branch, path, common directory and owner record. `ship.ts` defines the ship path interface, classifies `task.ps1` sentinels for the scaffold adapter and provides a dry-run path. `ops.ts` loads `aidlc.ops.json` (operation roles, bindings, environments, health signals) and executes or looks up bound operations.

`src/artifacts/` is the playbook artifact chain. `frontmatter.ts` parses the scaffold's front matter conventions. `card.ts` parses, validates and renders task cards and computes the tier. `intent.ts`, `spec.ts` (EARS classification) and `plan.ts` (definition-of-ready gates, task-split parsing) cover stages 1-3.

`src/providers/` abstracts model calls: `types.ts` (interface, invocation ids, JSON extraction), `mock.ts`, `claude-api.ts` (Anthropic SDK, default model `claude-opus-5-5`, adaptive thinking, an explicit `output_config.effort` on every request and none of the settings Opus 5.5 rejects, quota/refusal outcomes, an injectable messages client for tests), `claude-code.ts` (`claude -p --output-format json`; an `is_error` payload is an error, or a quota hold by its `api_error_status`). `claude-code.ts` adds `--effort <level>` after the model only when it is constructed with `forwardEffort` (the `claudeCode.forwardEffort` key, which `aidlc run` and `aidlc evals run` both read); when disabled, aidlc does not synthesize an effort argument, and existing extra arguments, environment and Claude Code settings remain effective; with `forwardEffort` on and `CLAUDE_CODE_EFFORT_LEVEL` among the keys of its launch environment it starts no process and returns an error. For calls that pass the pre-launch checks, a request with `recordToolCalls` runs `claude-code.ts` with `--output-format stream-json --verbose` and gets the `tool_use` blocks of the run as `toolCalls`; the `result` event is read as the payload, and a stream with no `result` event is an error.

`src/maintain/` closes the loop: `bands.ts` (rolling baseline, Western Electric rules, tiers from `bands.yaml`), `incident.ts` (deduplicated incident ledger and intent.md writer).

`src/evals/runner.ts` loads `evals/*.json` (refusing a prompt that names the measurement), runs an optional model step and deterministic checks, including checks over the tool calls the model made, and gates on a pass rate; a model-backed case runs in a detached temporary checkout of HEAD with an empty temporary `AIDLC_STATE_DIR`, both removed afterwards; `runTrials` runs the cases n times, with `--variant` alternating a checkout of HEAD and one of the ref, and gives the `compareTrials` verdict for HEAD against the ref on the pass rate (docs/OPERATIONS.md, Evals).

`src/review/bench.ts` is the reviewer bench (`aidlc review bench run` and `aidlc review bench export`): the run scores a stage's primary reviewer on the confirmed cases under `evals/review/`, each candidate reviewed once in a detached temporary checkout through the loop's own prompt and panel functions, the export drafts unconfirmed cases from the card runs `src/cli/main.ts` hands it and pins each candidate under `refs/aidlc/bench/`, and the module imports nothing from `src/state/`, `src/coordination/` or `src/loop/` (docs/OPERATIONS.md, Reviewer bench).

`src/core/trial-compare.ts` is the pure verdict of `aidlc review bench compare` and of `aidlc evals run --variant`: `trialRange` gives the median, minimum and maximum over trials, and `compareTrials` returns `better`, `worse`, `no-measurable-difference` or `inconclusive` with a one-line reason, deciding by recall, then by the false-block rate, only when the two ranges do not overlap; the names it takes can drop the second metric, as the eval variant run does with the pass rate in the place of recall. `src/review/bench.ts` builds the `summary` it reads with `--trials <n>`.

`src/core/env-name.ts` reads one variable by name from an environment object passed in, in any letter case on win32, the exact spelling first, with an empty value counted as missing; `killProcessTree`, `listProcesses` and `resolveWorktreeRoot` read `SystemRoot`, `windir` and `SystemDrive` through it.

`bench/` (outside `src/` and never shipped) holds the loop benchmark: `npm run bench` counts the modules, fs calls, child processes and output of each hook event and the CLI start, and compares them with the ceilings in `bench/baseline.json` (docs/OPERATIONS.md, Loop benchmark).

`src/audit/` provides the evidence manifest with sealing (`manifest.ts`) and the independent verifier (`verifier.ts`).

`src/config.ts` defines `ProjectConfig`, the zod schema of `aidlc.config.json` and its defaults; `loadProjectConfig` reads the file (an absent file gives the defaults, and one that is not JSON or fails the schema throws `ConfigError`) and `resolveWorktreeRoot` gives the directory card worktrees are created under. `src/index.ts` is the library entry point (`main` in `package.json`, built to `dist/index.js`) and only re-exports modules.

`src/hooks/index.ts` implements six of the seven Claude Code guards and `src/hooks/stdin-script.ts` the seventh, `stdin-script` (issue 463); `src/hooks/entry.ts` runs every guard that applies to an event in one process (`bin/aidlc-hook.js`, `aidlc hook auto`), so a tool call costs one node start. `src/hooks/lazy.ts` loads the modules only some hook events need (the router, the goal, lease and journal stores, and the planning claims, which alone load yaml) on a guard's first use, through `require` with the extension of its own file (card T0-HOOK-LAZY-2). Every `PreToolUse` or `UserPromptSubmit` event, whichever guards apply, first renews the card leases of the event's session on this host that have less than half of their TTL left (`renewSessionCardLeases`, through `LeaseStore.heartbeat` at each lease's generation), reading the lease files with node:fs once per UTC minute window per session (a marker under `<state>/heartbeat/` holds the window of the last scan) and loading the lease store only when one qualifies; a malformed lease, a lease released meanwhile (`LeaseStore.heartbeat` refuses it under its lock), a fenced heartbeat or a held lock skips that lease, and the renewal never changes the hook result and journals nothing. The goal controller counts a projected card run stopped for ownership whose card lease is unreleased and unexpired as running, so `aidlc next` waits on it instead of stopping the goal (card T0-CARD-LEASE-HEARTBEAT-2). `src/review/pre-review.ts` builds the pre-review (R2) prompt (the policy hash, sha256 of the applied REVIEW.md text, in its policy heading with the rule files the candidate changes; the delta since the last reviewed candidate on later rounds; the pre-review's advisory notes and the surviving mutants of the current candidate's report on the formal stage, in a section the formal prompt opens with the state of the mutant report: missing, unusable, for another candidate, or the counts of the sweep; a diff above the stage's byte cap is refused before dispatch, never cut), runs the configured second-model reviewer with a receipt and extracts the verdict (a reason tagged `[question]` or `[suggestion]` is advisory; a new finding outside the delta is a first-round miss, `outsideDelta`); the card runner gates SHIP on a fresh pass per candidate and per R3 cycle; with `formalReview.command` set the same module runs R3 (Codex here, with `formalReview.fallback`, Claude Opus 5.5 here, dispatched while the primary holds an unexpired quota hold on the card, each reviewer in its own pool, one shared ledger) and feeds the existing review ledger, so a block is REVIEW_FIX and the repaired candidate restarts the pre-review cycle. Both prompts carry the repository's learned invariants after the policy section: `reviewLessons` (`src/artifacts/lessons.ts`) reads the NEVER and ALWAYS lines of `docs/LESSONS.md` newest first under `REVIEW_LESSONS_MAX_BYTES` and returns them with the count the cap left out, and the card runner reads them with the other prompt inputs of each dispatch. In `preReview.coverage: shadow` the `ac-coverage` angle is also asked for one `CoverageEntry` per acceptance item (the frozen `VERDICT_SCHEMA` is untouched, so a `{schema}` reviewer never sees the field), and `joinCoverage` labels every item across the angles into the `RoundCoverage` the round record, the `PRE_REVIEW_DECIDED` event, the round document and the R2 summary retain without any of them reading it for a decision. `src/review/stats.ts` summarises both ledgers over the persisted card runs: rounds, decisions, blocks, durations, findings by disposition, re-raises and first-round misses per card, and the totals of a family of superseded cards, with the repro counts (`aidlc review stats`). `src/review/mutant-gen.ts` lists the mutants of the `src/` TypeScript lines a zero-context diff adds under eight fixed operators, with an in-house scanner that keeps comments, strings, template literals and regex literals out of reach; it is pure and adds no dependency (card T1-VERIFY-MUTANT-GEN). `src/review/mutants.ts` runs those mutants one at a time under a card's DoD (`aidlc card mutants`), restores each file from the bytes it read and writes an advisory report bound to the candidate commit under `.review/`, which no gate reads. `src/review/repro.ts` runs `aidlc review repro`: the author's repro argv of a finding, without a shell, in a temporary detached checkout of the reviewed candidate (with the `--files` paths taken from the current candidate) and in one of the current candidate, each with the main checkout's `node_modules` linked and a new empty `AIDLC_STATE_DIR`, all removed afterwards; it records both exits as `ReviewFinding.repro` under the card-run lock, which the `## Prior findings` prompt section and the review statistics read and no gate does (card T1-FINDING-REPRO-2). `src/loop/` contains the directive contract, the goal controller, the card runner, the release runner and `run-driver.ts`. The run driver asks the controller for one directive, sends actionable work to the command-capable provider, then rereads persisted state; it owns no state file or report transition and stops on human gates, review blocks, quota holds and deadlines. `context-pack.ts` builds the context pack of the controller's `run-card` directive (`loadContextPack`): the card's plan section, acceptance, `allow_paths`, `non_goals` and the lesson lines of `docs/LESSONS.md` that name its paths or modules, as JSON within a byte budget that drops lessons first and then shortens the plan section, never the acceptance list, read only from the plan file and `docs/LESSONS.md` inside the main checkout. `src/scaffold/init.ts` copies `templates/` over a repository. `src/cli/main.ts` wires everything with commander. A command that names a card resolves its goal with `resolveCardGoal` (`src/core/card-goal.ts`) from the goals that project the card, never from which goal is newest (card T0-CARD-GOAL-RESOLVE). Before any card run is read or written, `card next`, `attempt`, `close`, `report` and `review pre`, `r3`, `dispute`, `accept` refuse a goal that is terminal or in `STOP` or `DONE` with `terminalGoalRefusal` from the same module, the predicate of the goal dispatch guard, naming the goal, its state, the stop reason and `aidlc goal extend` (a time stop, or `STOP` left by the resume of one) or `aidlc goal resume`; `card status`, `takeover`, `ci-reconcile`, `withdraw`, `mutants` and `review findings`, `repro` are not refused (card T0-CARD-TERMINAL-GOAL-2, replacing T0-CARD-TERMINAL-GOAL). The CLI resolves and checks the goal from one `GoalStore.listGoals` read and passes that record to `ensureCardRun`, with no reload before the first card-run access; `card close` registers its exit sweep after the check. A stop saved by another process after that read is outside it (no goal-record lock) and shows in `aidlc audit verify` as `WORK_AFTER_TERMINAL`.

The ranked order of the directories of `src/` is the order of the Layers sentence of `CLAUDE.md`, inner to outer: `core/`, `scaffold/`, `probes/`, `state/`, `coordination/`, `delivery/`, `review/`, `loop/`, `hooks/` and `cli/`. The unranked units `artifacts/`, `audit/`, `evals/`, `maintain/`, `providers/`, `config.ts` and `index.ts` have no place in that order. `tests/surface/layers.test.ts` reads every import under `src/` from the syntax tree and checks four rules. Rule 1: a file of a ranked directory imports no file of a ranked directory that comes after its own directory in the order, and no import is exempt. Rule 2: a file under `src/core/` imports no file of another top-level unit of `src/` and no Node built-in other than `crypto`, named with or without the `node:` prefix. Rule 3: the graph of the top-level units of `src/`, where a unit is a directory or a root file by its name, has no cycle. Rule 4: every top-level unit is ranked or unranked, taken from the list of source files, so a unit whose files import nothing and are imported by nothing is checked too.

## Goal state machine

The goal deadline is fixed at intake: `createGoal` (`src/loop/controller.ts`) takes the goal's card from the request text only when the router counts exactly one card, a request naming several known card ids leaves the count unknown, and an explicit T1 or T2 size always gets the arc limit (card T0-GOAL-CARD-COUNT). A request gives a card when its `ref` is a card id, as with `--card`: when its text names a card id, `classifyRequest` (`src/core/router.ts`) names the given card in `ref=` and in the card reason, so where `createGoal` reads the goal's card from the reasons, with no `cards` option and a count of one card, the goal's card is the given card and not the card of the text (card T0-GOAL-CARD-REASON).

A recorded deadline extension re-admits a goal stopped for time (re-entering through `CARDS`) and the time-stopped card runs of its current projection (stops cleared, runs in progress again, card deadlines moved to the new goal deadline, journaled as `GOAL_STATE` and `CARD_STATE`; a superseded card keeps its stop), and moves the deadline of every run of that projection still in progress to the new goal deadline when that is later (journaled as `NOTE`, card T0-EXTEND-RUNNING-CARD); a resume carrying a revision applies it before the projection (re-entering through `CARDS`, the completion evidence of the old projection reset to pending), so replacement cards run in the resumed generation; delivery evidence is bound to the generation, so no earlier release is reused. While a T2 goal is in `CARDS` without the plan checkpoint for its current revision, `card next` parks its cards (`wait`) until the approval is recorded. A goal parked in `WAIT` (polled while its cards were still running) resumes to `RUN`, journaled as `GOAL_STATE WAIT->RUN`, before `VERIFY_ARC` is derived once every required card is closed; the diagram has no `WAIT -> VERIFY_ARC` edge.

Source: `GOAL_TRANSITIONS` and guards in `src/core/goal-machine.ts`.

```mermaid
stateDiagram-v2
  [*] --> PLAN
  PLAN --> CARDS: intent accepted / plan produced
  PLAN --> WAIT
  PLAN --> STOP: unresolved decision, planning allowance exhausted
  CARDS --> RUN: projection validated and authorized
  CARDS --> PLAN
  CARDS --> STOP: rejected checkpoint
  RUN --> RUN: next ready card
  RUN --> WAIT: child or external result pending
  RUN --> VERIFY_ARC: required cards closed
  RUN --> STOP: no admissible work
  WAIT --> RUN: evidence permits progress
  WAIT --> PLAN: accepted revision
  WAIT --> CARDS
  WAIT --> DELIVER
  WAIT --> STOP
  VERIFY_ARC --> CARDS: one bounded repair cycle
  VERIFY_ARC --> CLOSE: development target verified
  VERIFY_ARC --> DELIVER: package / staging / production requested
  VERIFY_ARC --> STOP: repair cycle exhausted
  VERIFY_ARC --> PLAN: accepted revision that adds an unmerged card
  DELIVER --> WAIT
  DELIVER --> CARDS: in GOAL_TRANSITIONS; no report result takes it
  DELIVER --> CLOSE: target verified
  DELIVER --> STOP
  CLOSE --> DONE: closure predicates hold
  CLOSE --> STOP
  DONE --> [*]
  STOP --> [*]
```

Guards: `CARDS` from `PLAN` needs accepted intent; `RUN` needs an authorized projection (T2: a `plan-checkpoint` authorization for the current revision); `VERIFY_ARC` needs all required cards closed (an empty ready set with gaps is WAIT or STOP, never DONE); `DELIVER` is refused for a development-only goal; a non-development target must pass `DELIVER` before `CLOSE`; `DONE` needs complete closure; `PLAN` from `WAIT` or `VERIFY_ARC` needs an accepted revision; `CARDS` from `VERIFY_ARC` needs the one repair cycle (`arc-failed`); `DELIVER --> CARDS` is in `GOAL_TRANSITIONS`, but no report result takes it; terminal goals refuse every transition until `resume` links a new generation.

`finalStateForTarget` fixes where each target ends: package after PREPARE, staging after STAGE, production and migration after OBSERVE. A recovered attempt closes with disposition `recovered`, never `delivered`. `aidlc release report` (`ReleaseRunner.reportStep`) records only the manual step the state asks for, with `succeeded`, `failed` or `UNKNOWN` (`package-run-proof` in PREPARE of a `package` attempt whose candidate and configuration prerequisites are met, `stage-verify` in STAGE after a succeeded `stage-deploy`, `recover-verify` in RECOVER after a succeeded `recover`, none of them once stored as `failed`), refuses any other report before any write, and `release next`, once it reaches the case of the attempt's state, saves STOP/release-health on a stored failed `stage-verify` in STAGE (`staging verification failed`), `recover-verify` in RECOVER (`recovery verification failed`) or `package-run-proof` in PREPARE of a `package` attempt (`package install/run proof failed`) (card T0-RELEASE-REPORT-STEP). In OBSERVE a runner built without `signals`, as `aidlc release next` builds it, runs the first bound `health` operation once per evaluation when `aidlc.ops.json` declares a `health` signal and binds the role, the attempt names its environment and the binding's directory is an existing directory, with no ledger record, no lease and no publication, effect or authority check, and maps each declared signal to one `HealthSignal` whose observation comes from the last non-blank stdout line of a succeeded run that names the attempt's environment (by its lease file) and candidate; unsuccessful execution receipts and invalid reports produce unavailable signals, and runner exceptions propagate without completing the evaluation (card T0-HEALTH-OP-SIGNALS).

`ReleaseRunner.next` runs the step logic, whose nested steps call the step logic again, and then one exit that every return passes: for an attempt in DONE or STOP, inside the attempt's section (`release-attempt:<attemptId>`, taken when the attempt names an environment) the exit releases each environment lease the attempt claimed that is still this session's on this host and whose operation names the attempt (`release:<attemptId>`), so a cleanup run by another session releases nothing, in that lease's own section, one at a time, which reads the ledger again and leaves the lease held while a record of the attempt (`releaseOperationOf`) or a record targeting that environment (the same lease file) is `intended`, `issued`, `running` or `UNKNOWN`, and `issue` of an attempt that names an environment records a step's intent under the same two sections only while the attempt holds that lease (card T0-STAGING-LEASE-RELEASE-2).

## Card state precedence

`selectCardState` in `src/core/card-machine.ts` evaluates evidence in this order and returns the first match:

1. Unknown operations exist: WAIT (no new mutation), or STOP/time once the reconciliation grace has expired.
2. A terminal record, a stale ownership generation (STOP/ownership) or a capability blocker (STOP/capability).
3. Merge verified and closure complete: DONE.
4. A known operation still running: WAIT.
5. Merge verified, closure incomplete: CLOSE. The closure predicates are metadata, docSync, findings, evidence, cleanup, lessons and followups; `lessons` needs a lesson line appended to `docs/LESSONS.md` (frozen format owned by `src/artifacts/lessons.ts`; every write is an append, the header and the first line going out in one exclusive append, so no writer overwrites another and existing bytes are never rewritten; a retry reuses the line journaled as pending, so a completed append is recognised even after a date rollover) or a recorded reason to skip, both journaled as EVIDENCE_RETAINED (a lesson as pending before the file changes and as recorded after), and `card close --all` never asserts it. `followups` (card T1-REVIEW-FOLLOWUP-ISSUE-2) records the one `review-followup` issue of the run's advisory and deferred findings, or why there is none: `CardRunner.recordFollowups` looks the issue up by its marker, else stores `followupPending` and submits it once, and while `followupPending` is stored it only looks up, so a pending submission is no operation and keeps the run in CLOSE; `card close --skip-followups` ends it with a reason. The reservation and the disposition hold the card-run lock and then the card lease lock, and there re-read the run (CLOSE, merge verified, step open, the caller's lease generation), fence the lease on a fresh clock reading and re-read the goal (not terminal, the caller's generation); the disposition appends a `NOTE` with the kind `followups-recorded` there, right before its write. Limits: a run closed before the step gets no issue; a step recorded with null files none later; a goal cancelled or a step skipped after the reservation does not recall the request; a crash between the reservation and the request leaves the run with no issue until the operator skips the step; and no operation is recorded, since an UNKNOWN operation moves the run to WAIT, where `card close` refuses. Every write of `card close` merges only its own changes into the run as stored under those two locks. Closure flags are accepted for a CLOSE run of a live goal only (the persisted goal decides, read again right before any write), with a verified merge and a present card lease that is fenced like every other mutation; the lease is the serialisation of a card's closers, every lessons write is an append and a retry reuses the pending line, so no line is written twice. CLOSE reads the stored run (a stale `card next` never undoes a recorded disposition), renews the card lease for its owner and lets a replacement session take over an expired one once no delivery operation is unresolved; an ownership stop of a merged card is reconciled once the blocking lease is gone. The raw card patch sets neither closure predicates, the follow-up fields, merge evidence, lease generations nor a CLOSE or DONE state, and a run persisted as DONE before the predicate existed stays DONE at card and goal level. PREPARE hands the card the same file with its count and most recent lines. `card close --cleanup` and `--metadata` do the step and record it: cleanup copies `.review/` into the evidence tree and removes the worktree, metadata writes `status: merged` in the main checkout, and the session commits that file on main. `card close --evidence` checks that the goal manifest holds an intact file retained with `aidlc evidence retain --card <id>`, and any kind counts. `aidlc worktree reclaim` removes the clean worktrees of merged, superseded and cancelled cards, and `card close --cleanup`, `card close --all` and `goal cancel` run it; the branch stays and `.review/` goes to the evidence tree. `src/loop/worktree-reclaim.ts` holds the copy, the removal and the sweep.
6. Admission deadline reached: STOP/time.
7. Review allowance exhausted (STOP/review) or repair episode exhausted (STOP/card).
8. No validated run context: PREPARE.
9. Fresh substantive block with allowance left: REVIEW_FIX.
10. Acceptance work incomplete (no RED/DoD receipt, dirty candidate, code-caused CI failure): BUILD.
11. Candidate ready, no active operation, merge incomplete: SHIP.

## Directive contract

`src/loop/directive.ts`. Every directive carries `goalId`, `generation`, `revision`, `goalState`, `deadline`, a `narration` and `skills` (the companion skills the step calls for, from the goal routing: `tdd`, `diagnose`, `grilling`, `merge-conflicts`; advisory names, never a gate). Kinds:

| Kind | Payload | Meaning |
|---|---|---|
| `ask` | question, options, responseRoute | one sizing/identity question the context cannot resolve; the revision that answers it (`aidlc goal amend <id> --text "<answer>"`) re-classifies the revised text with the router and stores only the new question (none removes it), and every other routing field is the retained intake route (card T0-ASK-RECLASSIFY) |
| `plan` | size, inputs, invocationAllowance, outputs, lessons | produce the plan at the routed depth; `lessons` is the count and the ten most recent lines of `docs/LESSONS.md`, which every card is checked against before it is registered |
| `project-cards` | planRef, cardsDir, outputs, lessons | write/validate cards; human sign-off owns the registry; `lessons` as for `plan` |
| `checkpoint` | approvalKind, packet, responseRoute | T2 plan+projection approval, or a production approval packet |
| `run-card` | cardId, cardState, worktree, base, mode, effort, role, cardDeadline, context | run one card through `aidlc card next` |
| `verify-arc` | cards, integratedChecks, repairCyclesLeft | verify the whole goal on the integrated artifact |
| `release` | attemptId, releaseState, target, environment, packet | drive the release attempt; at CHECKPOINT of a production or migration attempt `packet` is `ReleaseRunner.checkpointPacket`'s (the production environment and planned operations the authority is matched against, while `environment` stays the attempt's recorded one), `{}` otherwise |
| `wait` | on, until, pollSeconds | attach to one known signal |
| `close` | missing | perform only the missing closure steps |
| `done` | evidence | return the existing result |
| `stop` | stop record (reason, detail, nextAction, global, unresolved operations) | preserved partial effects and the precise next action |

`ReportResult` values accepted by `aidlc report --result`: `intent-accepted`, `plan-produced`, `plan-failed`, `cards-projected`, `approved`, `rejected`, `card-result`, `arc-verified`, `arc-failed`, `release-result`, `revision`, `cancel`, `resume`. A report carrying a stale `generation` is refused.

Report results by goal state (card T0-CARDS-PROJECTED-REENTRY). A listed card is merged when the card registry records it with status `merged` or this goal's run of it has `mergeVerified`; only the cards the goal lists now count.

| Result | PLAN | CARDS | RUN, WAIT | VERIFY_ARC | DELIVER | CLOSE |
|---|---|---|---|---|---|---|
| `cards-projected` | accepted, to CARDS | accepted | accepted | refused | refused | refused |
| `arc-verified` | refused | refused | refused | accepted only when every listed card is merged | refused | refused |
| `arc-failed` | refused | refused | refused | accepted, one cycle | refused | refused |
| `revision`, every listed card merged | accepted, stays | accepted, stays | accepted, to PLAN | accepted, stays | accepted, stays | accepted, stays |
| `revision`, a listed card not merged | accepted, stays | accepted, stays | accepted, to PLAN | accepted, to PLAN | refused | refused |

STOP and DONE accept `resume` only. A refusal throws before any journal entry or goal write. The `cards-projected` refusal comes before the registry is read and names the routes: in VERIFY_ARC `aidlc goal repair <goalId> --cards <new ids>` or `aidlc goal amend <goalId> --text "<request>" --cards <ids>`, in DELIVER and CLOSE `aidlc goal cancel <goalId>`, then `aidlc goal resume <goalId> --text "<request>" --cards <ids>`; the `revision` refusal names the same cancel and resume. While a listed card is not merged, the `verify-arc` narration names it. Before this card, `cards-projected` moved VERIFY_ARC and DELIVER to CARDS without spending the repair cycle, `arc-verified` read only the goal state, and a revision in VERIFY_ARC, DELIVER or CLOSE kept the state.

Within one outermost `next`, `report` or `createGoal` call of `GoalController`, the card registry is read at most once after a successful load, and a load that throws is not kept, so a later step of the same call loads again; a change to a card file after that load becomes visible to a later call that loads the registry (card T0-REGISTRY-PER-CALL).

## Evidence and audit chain

1. Every controller, card runner and release runner action appends a `JournalEvent`; each event hashes its canonical JSON plus the previous hash. `Journal.verify()` detects malformed lines, sequence gaps, prev-hash mismatches and altered events. `GoalController.ensureCardRun` saves a new run with `CARD_DISPATCHED` owed and appends it in the lock section of that save, so the next `aidlc card next` or `aidlc card attempt` recovers a lost append with `completed` true (card T0-SIDE-WRITE-FAULTS). A failed board write beside a goal stop journals a NOTE with `boardError` and keeps the stop, since the board is a view. The card runner appends an attempt, R2, R3 or merge-result event only after the card-run write that commits its decision, which records the event as owed (`CardRun.journalOwed`); an append that did not land is made by the next card-run command on the card, so each such event reaches the journal once and never ahead of its record (card T0-JOURNAL-FAULT-EVENTS).
2. `EvidenceStore.retain` copies artifacts into `evidence/<goalId>/` and records sha256, size, candidate digest, environment and invocation id. `seal` binds the manifest to the journal head hash, event count, final SHA/digest, models and host, and computes a digest over the canonical manifest. Both write `manifest.json` only inside an `updateJson` section (lock file `manifest.json.lock`, written through a temporary file and a rename with keys sorted), and `EvidenceStore.save` no longer exists (card T0-MANIFEST-LOCK). `seal` seals the manifest its section reads, so entries retained after the caller's load are sealed too; the argument stands in only when no file exists, its `models` replace the stored ones when it has the key, and the binding's `host`, when given, replaces the stored one; a sealed manifest is sealed again from its stored content. A binding passed as a function runs inside the section with the manifest being sealed: `aidlc audit seal` appends `MANIFEST_SEALED` there with that manifest's entry count and binds the seal to the event `Journal.append` returns (`journalHead` its hash, `journalEvents` its seq plus one), with no second read of the journal head. Lock order: the manifest lock is taken with no aidlc lock held, and while it is held the only lock taken is the journal lock of `Journal.append`, which takes none. Inside the section `retain` refuses, before any write and in this order, a sealed manifest, a file name reserved for the manifest's own files, then (card T0-EVIDENCE-ID-COLLISION) a file name that is empty, ends with a dot, is `review` (the `.review/` copy directory, ignoring case), has a Windows device name before its first dot (`CON`, `PRN`, `AUX`, `NUL`, `COM0` to `COM9`, `LPT0` to `LPT9`, ignoring case), or equals, ignoring ASCII case, the path of an entry of another id of the stored manifest, and only then a missing `--file`; the name rules are the same on every platform. A retain of an id the manifest holds replaces its entry, except that rule (the other id's file) refuses either id of a legacy manifest whose two ids share a path. Before the store is called, `aidlc evidence retain` refuses the entry that `verifyAudit` would report as `EVIDENCE_STALE_CANDIDATE` through the merges of its card (`staleCandidateRefusal`; card T0-RETAIN-STALE-CANDIDATE); a file of a candidate that did not merge takes the kind `earlier-candidate`, which is not candidate-bound.
3. `verifyAudit` reports a level: `none` (no events), `recorded` (events exist), `traceable` (chain intact, every operation intent has a result or explicit UNKNOWN, delegated work carries invocation ids, no work after a terminal event), `independently-verified` (additionally the seal verifies, artifacts match their digests, the sealed manifest names a final candidate digest, and every entry of a candidate-bound kind (`dod-receipt`, `review-verdict`, `ci-run`, `test-output`, `health`) names a candidate digest; that digest is compared with the digests of the succeeded merges of the entry's card when the journal records one, otherwise with `VerifierInput.finalCandidateDigest` only when it is supplied and not empty, and the CLI supplies the manifest's final digest; card T0-AUDIT-BINDING). Non-mutating events after the seal (closure bookkeeping) are a `MANIFEST_TRAILING` warning; a mutation after the seal makes it `MANIFEST_STALE`. A "fully audited" claim is `verified` only at that level with a host capture boundary asserted; otherwise `BLOCKED/capability` with the prerequisite named.
4. The merge result of a card shipped on the GitHub path carries `ShippedFacts` (`src/core/types.ts`: `headSha`, `mergeSha`, `tree`, `pr`), which the card runner reads from `gh pr view` and `git rev-parse <mergeSha>^{tree}` when it verifies the merge; `verifyAudit` takes injected git and gh probes (`aidlc audit verify` passes real ones) and re-derives each fact with `git cat-file -t`, `git rev-parse <mergeSha>^{tree}`, `git merge-base --is-ancestor <mergeSha> <base>` and `gh pr view <pr>`. A disagreement is a `FACT_MISMATCH` block, a fact that cannot be re-derived is a `FACT_UNVERIFIED` warning, no check reads a narration or free-text field, and a "fully audited" claim also needs at least one re-derived fact for every shipped card. The facts ride in the one merge result only when they can all be read; a shipped card whose merge result carries none is a `FACT_MISSING` warning and blocks a "fully audited" claim.

## Ship path adapters

`ShipPath` (`src/delivery/ship.ts`) has three methods: `ship`, `readVerdict`, `readMergeToken`.

- `ScaffoldShipPath` runs `pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/task.ps1 -TaskId <id> -Phase ship [-Base b] [-Local] [-SkipRed] [-NoAutoMerge]` from the main checkout and classifies output with `SENTINEL_MAP`: `[SHIP-EFFECT-UNKNOWN]` (read before the exit-zero contract, a whole-receipt timeout and every other sentinel, as `effect-unknown`, its line the detail; card T0-SHIP-TIMEOUT), `[SHIP-MERGE-FAIL]`, `[CI-GATE-TIMEOUT]`, `[CI-GATE-RED]` family, `[R3-SPEC-BLOCK]`/`[R3-ROUND-CAP]`, the `[R3-*]` no-verdict family, `[SHIP-NO-REVIEWER]`, `[SHIP-PR-*]`, `[SHIP-PUSH-FAIL]`, `[CARD-BUDGET-*]`, `[SHIP-SCOPE-*]`, auth guard text, RED evidence text, secrets, license, verify and DoD failures. The saga leg report comes before the order of the map (card T0-SHIP-SAGA-LEG): it is the last line holding `[SAGA-FAIL]` when, trimmed of white space, it reads `[SAGA-FAIL] <leg>` or `[SAGA-FAIL] <leg> (= first pending leg)`, with `<leg>` exactly one of `card-check`, `DoD`, `verify`, `commit`, `scope-gate`, `budget-gate`, `license-gate`, `leak-gate`, `push+PR`, `R3-review`, `CI-gate`, `merge` and `local-merge`. A report naming `DoD`, `verify`, `license-gate` or `leak-gate` makes that leg's class (`dod-failed`, `verify-failed`, `license-blocked`, `secrets-blocked`) the outcome, with the detail and failing line of that class's rule when the rule matches the output, else the detail `saga leg <leg>`. A report naming another leg, or a between-legs failure `[SAGA-FAIL] <operation>; first pending leg after it = <leg>`, keeps the license, secrets, verify and DoD text rules from deciding; any other last `[SAGA-FAIL]` line, or none, leaves the map unchanged. It reads `<worktree>/.review/<branch>.json` and `.rounds`, the RED receipt `.review/<id>.red` and the merge token `.git/scaffold-merged/<id>`.
- `GitHubShipPath` (`src/delivery/github-ship.ts`) is the native path for repositories without the PowerShell scaffold: commit, a fresh candidate-bound verdict written by the reviewer role at `<worktree>/.review/<branch>.json` (with `github.requireVerdict` on, a file whose `run_status` member is anything but the string `success` is no verdict, `[R3-NO-VERDICT-JSON]`, read before its block and its sha; both ship paths read a `run_status` outside the five values as `malformed`), a read-only PR reconciliation (a merged PR for the branch ends the ship as `merged` before any sync; an open one is reused after the push and names every later failure; a lookup problem without a PR, a failed listing, a malformed one or an entry that does not parse as a PR record fails as `[SHIP-PR-BASE-UNKNOWN]` before any sync, never as an exception), base sync, push, PR, CI check runs green, squash merge matching the head commit, merge token. Every direct call of the path runs under a timeout and a tree kill (card T0-SHIP-TIMEOUT): `git add -A`, `git diff --cached --quiet`, `git commit` and the local merge 60 seconds, `git push` 300 seconds, `gh pr create`, `gh pr merge`, and the `gh pr view` and `gh pr edit` of the text of a reused pull request 120 seconds, each capped by a request `timeoutMs` that is a whole number from 1 to 2147483647 and never a deadline of the whole ship; a push, PR create or merge that timed out or ended without an exit code ends the ship with `[SHIP-EFFECT-UNKNOWN]` and no later step, and a `git add`, staged-diff read or `git commit` that did not finish, or a staged-diff read with an exit code other than 0 or 1, with `[SHIP-COMMIT-FAIL]`. The base sync runs before any remote effect and before the local merge: remote mode fetches the base into `refs/remotes/origin/<base>`, local mode first checks that the main checkout has `refs/heads/<base>` checked out (the full `git symbolic-ref --quiet HEAD`, never the short name, which a tag of the same name makes ambiguous; another branch or a detached HEAD fails the ship before any sync or merge) and takes `refs/heads/<base>`, and `git merge-tree --write-tree HEAD <ref>` (git 2.38 or newer) tests the merge without touching a ref or the worktree. Clean: one log line, the reviewed head is the commit pushed, gated and merged. Conflict: the same merge is started in the worktree with `--no-commit` (the markers stay for the merge-conflicts skill, the branch head never moves inside the path) and, once `MERGE_HEAD` proves the merge is in progress after exit 1 (a conflict is a state git left behind, never a line of text: any other exit, or exit 1 without a `MERGE_HEAD`, is `[SHIP-BASE-SYNC-FAIL]` with the merge output flattened on one line, so a file named `CONFLICT (content).txt` in an operational error never reaches the runner as a diagnostic), git's lines go on the ship output under `LC_ALL=C` with brackets and percent signs encoded as the gate lines encode check names (a path can never form a sentinel or a `[SAGA-RESUME]` marker; the diagnostic lines carry neither, so they stay verbatim), and `[SHIP-BASE-SYNC-CONFLICT]` classifies as `merge-failed`, which the runner maps to BUILD below. The resume command and the PR number of every result of the path come from its own state, never from the output text, and every failure detail of the path (verdict reasons, git and gh output, paths, the base name, the worktree path) is flattened to one line and encoded exactly once inside its `fail` helper, the CI gate lines being the one verbatim detail (their JSON carries encoded names the runner decodes), while command arguments stay raw. The base name is normalised exactly once (`req.base` without one `origin/` prefix) and names the PR target, the fetch refspec and the tested ref alike, so a branch literally named `origin/main` is one branch throughout. A failed fetch, an unresolvable base, a merge-tree error or a merge that completes although merge-tree reported a conflict (aborted; a failed abort is reported as still mid-merge, never as restored) is `[SHIP-BASE-SYNC-FAIL]` with git's stderr on the line, `merge-failed` without a diagnostic: STOP/tool with the resume command. Every step prints a scaffold-style sentinel so `classifyShipOutput` classifies both paths uniformly; `requiredChecks`, `ciTimeoutMs`, `ciPollMs` and a `sleep` function are injectable. The `github` config block (`requiredChecks`, `requireVerdict`, `ciTimeoutMs`, `ciPollMs`) reaches the path through `shipPathFor`; a required check-run name absent from the head is pending until the timeout, never satisfied, and every check that reports on the head must succeed. The text of a pull request the path creates comes from `prBody` (card T0-PR-SUMMARY): the `## PR summary` section of `<cardsDir>/<card>.md` in the worktree (`shipPathFor` passes the configured `cardsDir`; card T0-PR-SUMMARY-CARDS-DIR), then a rule and one line that names the card and the formal review, or, for a card with no valid section, the fixed line the path wrote before, with the reason on the ship output; `docs/OPERATIONS.md`, Ship gates, gives the form of the section. An open pull request the path uses again gets the same text after the push (card T0-PR-SUMMARY-REUSED): the path reads the current text with `gh pr view <n> --json body` and writes the new one with `gh pr edit <n> --body` only when the two differ and `shipWroteBody` returns true for the current text. Both texts are compared, and `shipWroteBody` reads its text, with each CRLF made LF and trailing white space removed; `shipWroteBody` is true exactly when the text is the fixed line or its last line is `Card: <p>. Formal review: pass.` or `Card: <p>. Formal review: no pass recorded for this commit.`, where `<p>` is `<cardsDir>/<card>.md` or `specs/tasks/<card>.md`, and any other text is one a person wrote, which the path keeps. The ship output holds exactly one `PR body:` line directly before `PR #<n>`: `PR body: updated, the PR summary of the card` or `PR body: updated, the fixed line (<reason>)` after an edit that exits 0, `PR body: unchanged`, `PR body: kept (the current text was not written by the ship)`, `PR body: not updated (could not read the current text: <detail>)` for a view that fails, times out, ends without an exit code or prints no JSON object with a string `body`, or `PR body: not updated (gh pr edit <detail>)` for an edit that fails, times out or ends without an exit code, each detail flattened and encoded as every other failure detail. The text is no gate: no read or edit result changes the outcome, the PR number, the CI gate or the merge.
- `DryRunShipPath` returns scripted outcomes and is what the tests and `shipPath: "dry-run"` use.
- `CardRunner.secondPassDue` (card T1-R3-SECOND-PASS): with `formalReview.secondPass` on, `formalReviewGate` holds the first R3 pass of a run from the ship and directs one more R3 with matched rules; `ReviewInvocation.secondPass` and the `REVIEW_DECIDED` data mark it, a run gets one, and `recordReviewOutcome` treats its pass as the repeated pass it is. No second pass is due once the run has `MAX_R3_DECISIONS - 1` or more decisions, so a first pass at decision 3 or 4 goes to the ship (card T0-R3-SECOND-PASS-ROOM): a second-pass block after a first pass at decision 3 would be decision 4, which can only stop the card. Between 2026-10-22 and 2026-11-11, 7 second passes ran after a first pass at decision 3; 4 passed and 3 blocked, and each block stopped its card (T0-CARD-LEASE-HEARTBEAT, T1-OUTCOME-USAGE, T1-OUTCOME-GITHUB). The replay of 2026-11-07 found 9 to 10 of 20 known defects with one pass and 13 to 14 with two, and blocked 1 of 10 clean cases with one pass and 2 with two. After 15 cards with it on, turn it off if fewer than 2 of its blocks were repaired as real defects.
- The lift of a stop for review (card T1-REVIEW-RULE-SHIP; `liftRuledStop` in `src/core/review-policy.ts`, called by `CardRunner.ruleFinding`): when a ruling of `aidlc review rule` leaves no unruled finding among the non-advisory, unresolved findings of the stopping decision, the same locked update sets `stopLifted` (`at`, `by`) on the stopping invocation, appends one invocation with `outcome` `pass`, `ruled: true`, reviewer `ruling:<by>` and the candidate digest and sha of the stopping invocation, clears the run's `stop` and sets its state to `SHIP` (R1). `substantiveDecisions`, `substantiveBlocks`, `noVerdictRetriesUsed`, the receipts and the deadline stay as they were (R2). The runner does not read an invocation that carries `stopLifted` as a recorded stop, in `assess` or in `formalAdmission` (R3). `CardRunner.ruledPass` finds the ruled pass by its own record, `ruled` and the candidate digest, so it is the standing decision of that candidate whatever invocation follows it and under any reviewer name: `preReviewGate` and `formalReviewGate` admit the ship with no pre-review and no review directive, `preReviewEligibility` answers eligible for that digest, `secondPassDue` is false, `preReviewAdmission` and `formalAdmission` refuse a review of that candidate, and the ship's recheck of the reloaded run admits it; a candidate with another digest gets nothing from it (R4). The gate writes the canonical document `.review/<card>.json` as a `pass` for the candidate sha whose `advisory` lists each ruled finding with its decision, `by` and reason, and `applyShipResult` reads that document back from the ship path as the ruled pass, adding no invocation and moving no counter (R5). The lifting update records in `journalOwed`, beside the ruling's `FINDING_RULED`, one `REVIEW_DECIDED` with `outcome: pass`, `ruled: true`, `by` and `ruledFindings`, the ids of the ruled findings of the stopping decision, all in the persisted event data; the command appends both, and an append that fails is made once by the next `aidlc card next` (R6). The command's output names `aidlc card next <card>` after a lift and, when the card deadline has passed, `aidlc goal extend`; no deadline moves (R7).
- The continuation of a stop for review (card T1-CONTINUE-CORE; `src/core/continuation.ts`; called by `CardRunner.continueStop`). A `CardRun` holds `continuations`, an array that defaults to empty, of entries with `at`, `by`, `reason`, `stop` (the `reason`, `detail` and `at` of the lifted stop, the reason `review` or `ci`) and the optional whole numbers `decisions` and `admits` (R1). `continueReviewStop` takes a run in STOP for review and an act (`at`, `by`, `reason`, optional `decisions`) and returns the entry, with `decisions` 1 when absent and `admits` equal to `review.substantiveDecisions` plus `decisions`, and the ledger in which each invocation with an unlifted `stopReview` carries `stopLifted` (`at`, `by`); no counter moves (R2). It throws, changing nothing, when the run is not in STOP, its stop reason is not `review`, the caller states that the formal reviewer is not a command, `noVerdictRetriesUsed` is above `MAX_NO_VERDICT_RETRIES`, `by` or `reason` is blank, or `decisions` is not a whole number from 1 to 4 (R3). `admittedDecisions` returns the `admits` of the last entry whose stop reason is `review`, else undefined (R4). Given that count, `recordReviewOutcome` compares a command reviewer's merge-blocking block with it in place of `MAX_R3_DECISIONS`, in both directions: at or above the count the decision is `stop-review` with a detail that names the continuation and the count, below it `review-fix` with `remainingDecisions` the count minus `substantiveDecisions` (R5). The re-raise stop of a command reviewer and every decision of a ship-path reviewer are the same with a count as without one (R6).
- `CardRunner.continueStop(goal, card, act)` (card T1-CONTINUE-REVIEW-2; called by `GoalController.continueCard`, whose command is `aidlc card continue`, card T1-CONTINUE-COMMAND) continues a run in STOP for review on the same card. One `GoalStore.updateCardRun` applies `continueReviewStop` to the record read inside the card-run lock and writes the continuation, the lifted ledger, no `stop`, no `blocker` and the state BUILD, from which `selectCardState` selects the next state as after `aidlc goal extend` (R1). The update leaves `review.substantiveDecisions`, `substantiveBlocks`, `noVerdictRetriesUsed` and `scriptCounter`, `findings`, the `outcome` of every invocation, `effort`, `ci`, `candidate`, `dodReceipt`, `redReceipt`, `blockedReceipt` and `deadline` as they were (R2). It owes one `CARD_STATE` event whose persisted data holds `from` STOP, `to` `readmitted` and `continuation` (`by`, `reason`, `stop`, the lifted stop's reason, `decisions`, `admits`); the runner appends it after the write, and the next `aidlc card next` delivers it once when that append failed (R3). While `admittedDecisions` of the run is a number, `formalAllowance` returns it, the assessment's `reviewExhausted` and `formalReview`'s call of `recordReviewOutcome` compare with it, `secondPassDue` compares with it minus 1, and the review directive's `maxDecisions` and the reviewer prompt's decision limit, both read from `formalAllowance`, name it, each in place of `MAX_R3_DECISIONS` and `MAX_SUBSTANTIVE_REVIEW_DECISIONS` (R4). The gate's stop detail and the admission's refusal then name the continuation's admitted count where they name the two-decision or the 4-decision allowance (R5). When `continueReviewStop` throws or the card has no run in the goal, the runner writes nothing and appends nothing (R6). When the blocking decision of a continued run is on the current candidate, `aidlc card next` selects REVIEW_FIX and returns, as for any run there, the `build` directive of the repair attempt, whose narration names the decisions left under the admitted count (R7). `baseSyncDue` and the ship-path reviewer keep their constants. The import of `src/core/continuation.ts` by `src/loop/card-runner.ts` raises the modules the built CLI loads at start from 253 to 254, one above what the `cli.start` ceiling of 241 admitted with its slack and allowance, so `bench/baseline.json` sets that ceiling to the measured 254 by hand. The ci branch (card T1-CONTINUE-CI) takes a run in STOP for `ci`: `continueCiStop` in `src/core/continuation.ts` refuses, before the write, a blank `by` or `reason`, a given `decisions`, a run with no effort episode and a ladder stop (the message names the ladder's reason), and otherwise returns the entry and the step of `afterShipFailure` on the run's episode with the cause `continuation by <by>: <reason>` and the `limitsPermit` of `refutePatch`. The update writes the episode of that step, the continuation with stop reason `ci` and no `decisions` or `admits`, state BUILD and no `stop`, `blocker`, `dodReceipt` or `blockedReceipt`, and leaves `ci`, `review`, `findings`, `candidate`, `redReceipt` and `deadline` as they were. Beside the `CARD_STATE` event (with `by`, `reason` and `stop` `ci`) it owes the `ATTEMPT_FINISHED` of the refuted success with `refutedBy` `continuation` and the `ATTEMPT_STARTED` of a promoted running repair, with the data `refuteDirective` journals. The act appends the first two (`deliverOwed`); it passes the promotion's key as `hold`, so that event stays owed and the next `aidlc card next` appends it, after the controller's `GOAL_STATE` re-admission. No other caller passes `hold`.
- The contract of a card run (card T1-CARD-CONTRACT-2; `src/core/contract.ts`, pure). `contractDigests(card)` returns one SHA-256 hex digest for each of `requirements`, `acceptance`, `allow_paths`, `forbid`, `non_goals`, `dod_command`, `dod_exit`, `budget` and `tdd` (`CONTRACT_FIELDS` in `src/core/types.ts`), computed over `JSON.stringify` of the value the parsed card holds, with an absent `requirements`, `forbid` or `non_goals` taken as an empty list and an absent `budget` as `null`; the digest is over the parsed value, so a layout the parser reads the same way, or text it does not read (an indented line after a list item), changes no digest (R1). When `GoalController.ensureCardRun` is called for a card with no run in the goal that the registry of the main checkout holds, it creates the run with `contract`, the nine digests of that card as the registry holds it at that call (R2). When the registry does not hold the card, it throws `card <id> is not in the card registry: no run is created`, before any write and any journal append (R3). A card that has a run gets that run as it is, whether or not the registry still holds the card (R4). `changedContractFields(recorded, card)` returns, in the order of R1, the fields whose recorded digest differs from the card's or is absent from the record (R5). `invalidatedBy(changed)` returns `dod` when they hold `acceptance`, `dod_command`, `dod_exit` or `tdd`, `review` when they hold `requirements`, `acceptance`, `allow_paths`, `forbid` or `non_goals`, both when both hold, and neither for `budget` alone and for no field (R6). `amendedDigest(digest, count)` returns `digest` for a count of 0 and otherwise the SHA-256 hex digest of the previous result, a line feed and `amended`, applied `count` times (R7). The `CardRun` schema holds an optional `contract`, a record from contract field to digest, and `amendments`, an array that defaults to empty, of `CardAmendment` entries with `at`, `by`, `reason`, `revision`, `changed` (contract fields) and `invalidated` (`dod`, `review`) (R8). The act is `CardRunner.amendCard` (next item); the command is `aidlc card amend`, card T1-AMEND-COMMAND.
- `CardRunner.amendCard(goal, card, act)` (card T1-CARD-AMEND; the command is `aidlc card amend`, card T1-AMEND-COMMAND) records the owner's amendment of a started card, a change a commit to the card file already made; it edits no card. Given `by` and `reason` on a run whose recorded `contract` differs from the digests of `card`, one `GoalStore.updateCardRun` appends to `amendments` an entry with `at`, `by` and `reason` (trimmed), `revision` one above the run's `cardRevision`, `changed` (`changedContractFields`) and `invalidated` (`invalidatedBy`), and sets `cardRevision` to that revision and `contract` to `contractDigests(card)` (R1). When `invalidated` holds `dod`, the update unsets `dodReceipt` and `blockedReceipt` and reopens a succeeded effort episode with `reopenAfterReviewBlock` and the reason `amendment <revision>`, so the success that bound the candidate stays a success and the next attempt is admitted; an episode that is not succeeded stays as it is (R2). When `invalidated` holds `review`, the update replaces `candidate.digest`, and the `candidate` of each CI rerun equal to it, by `amendedDigest` of that digest applied once and unsets `blockedReceipt`; every review invocation and pre-review round keeps its digest, so the decisions recorded so far are decisions of an earlier candidate and every review rule reads the amended one as another candidate (R3). While a run holds n amendments whose `invalidated` holds `review`, `recordAttempt` records a candidate it computes (from the checkout probe or, on the dry-run path, from the commit) under `amendedDigest` of that digest applied n times, before the withdrawn-candidate check; a candidate the call keeps is not amended again (R4). In the same-candidate rules of `formalAdmission` and `preReviewAdmission` (`ofCurrentCandidate`), a review invocation or a pre-review round belongs to the current candidate when its digest is the candidate's, or when its commit is and the run holds no amendment whose `invalidated` holds `review`; on a run that holds one, a record under an earlier digest of the same commit is a decision of an earlier candidate, so an earlier pass or block on that commit neither satisfies nor refuses the new round or decision. No invocation, round, finding or counter is rewritten, and findings stay keyed by commit: the decision on the amended candidate resolves or re-raises them by the existing rules. The update leaves `state`, `stop`, `review`, `findings`, `continuations`, `redReceipt`, `deadline`, the candidate's commit, the outcome of every attempt and, without `dod`, `effort` as they were: the act lifts no stop, and `selectCardState` selects the next state from the evidence (R5). It throws with the cause and writes nothing when the card has no run in the goal, the run is DONE or has `mergeVerified`, an operation of the card is `intended`, `issued`, `running` or `UNKNOWN`, a formal review invocation is `pending`, the run has a pending repair, the run holds no `contract` (a run created before T1-CARD-CONTRACT-2), the contract equals the card's, or `by` or `reason` is blank after trimming (R6). The update owes one `NOTE` event whose persisted data holds `amendment` (`by`, `reason`, `revision`, `changed`, `invalidated`); the runner appends it after the write, and when that append fails the amendment stays recorded and the next `aidlc card next` delivers the event once (R7).
- The contract gate beside `CardRunner.amendCard` (card T0-CONTRACT-GATE-2; private `CardRunner.contractChanged`, `contractGate` and `refuseAmendedContract`). `contractChanged(card, run)` reads the card and that one record and nothing else: on a record that holds a `contract`, no `mergeVerified` and is not DONE it returns `changedContractFields(run.contract, card)`, on every other record nothing; it does not depend on whether `amendCard` would admit the amendment (R1). While it returns a field, `recordAttempt` refuses after delivering the owed events of the record it reads (R2); `preReview` and `formalReview` refuse after their refusal of a stopped run, before any reservation, pool request or reviewer (R3); and `assess`, called by `next` with `gated`, runs a dry assessment of the record it read (no save, no journal append, no lease claim) and refuses before any write when the selected state is BUILD, REVIEW_FIX or SHIP (R4); the dry assessment takes the record, lease, clock and `SelectionFacts` (the unresolved operations of the card and the kind of its worktree, each read where the selection first needs it and kept) of the assessment it guards, so the state it judges is the state `next` executes (R3 decision 1, F1). Each refusal carries one message naming the card, the changed fields, `aidlc card amend <card> --by <who> --reason <text>` and the restoring of the card text (R6). With the card the call read, the gate is asked again on the record locked for the pre-review round, on the record locked for the formal decision (`refuseAmendedContract`) and in `shipDrift` on the record the ship re-reads under the card-run lock, so an amendment another caller records during the call refuses the reservation or withdraws the ship (R5). The operator's view: `docs/OPERATIONS.md`, Amendments.
- `GoalController.continueCard(runner, goalId, card, act)` (card T1-CONTINUE-GOAL-2; the command is `aidlc card continue`, card T1-CONTINUE-COMMAND) continues a card on its existing run. Before it reads the card run it refuses a goal that `terminalGoalRefusal(goal, 'continue')` refuses (so it runs on a goal that is not stopped or is in STOP for `review` or `ci`), a `by` or a `reason` that is blank after trimming, and a `decisions` that is given and is not a whole number from 1 to 4 (R1). It then calls `runner.continueStop(goal, card, act)` once, except on the rerun of R5 (R2). A refusal, and a throw of `continueStop` before its write (no run for the card, or a run or an act that `continueReviewStop` refuses), throws with the cause and leaves the goal record, the card-run record and the journal as they were (R3). When the act lifted the card's stop and the goal is in STOP, terminal, with the stop reason of the lifted stop and in the generation the method read, it re-admits the goal in the section of the goal lock that `ruleFinding` also uses (`readmitAfterLift`): one `GOAL_STATE` with `from` STOP, `to` CARDS and `continuation` (`cardId`, `by`), then the goal written with `terminal` false, no `stop` and state CARDS; a goal not stopped, or stopped for another reason, is not re-admitted (R4). Called on a run out of STOP whose last continuation lifted a stop of the goal's stop reason and is not earlier than the `at` of the goal's stop, while the goal is still in STOP for that reason, the method records no second continuation and completes the re-admission with the `by` of the recorded one, appending the event only when none with `continuation` follows the goal's last `GOAL_STOPPED` (R5). When that continuation is earlier than the goal's stop, the method calls the runner, which refuses a run that is not in STOP; `ruleFinding` does the same with the `stopLifted.at` of the last lifted decision, and its runner refuses a run that is not stopped for review. On the rerun for a goal stopped for `ci`, a given `decisions` is refused with the message of `continueCiStop` before any write (card T0-SMALL-ISSUES-410-411-465). A failure after the runner's write (the delivery of an owed event, the `GOAL_STATE` append or the goal write) is thrown with its cause and nothing is undone: the continuation stays recorded, an event not appended stays owed and the next `aidlc card next` delivers it, and a later call completes the re-admission by R5 (R6). It returns the run, the goal, `continued` (this call recorded a continuation) and `readmitted` (R7). No deadline moves.
- `CardRunner.withdrawCandidate` (`aidlc card withdraw`, card T0-CANDIDATE-WITHDRAW) refutes a bound candidate no R3 decision has decided, or whose latest R3 decision is an advisory block (card T0-ADVISORY-WITHDRAW): `afterShipFailure` turns its success into a counted failure, and a `pendingRepair` of kind `withdrawn` keeps the finding and the candidate digest, so `pinnedCandidate` and `recordAttempt` refuse that candidate until a success records another one. A latest R3 decision on the bound candidate that is a pass or a merge-blocking block still refuses the withdrawal with the text that begins `R3 decided candidate`, and a candidate with a ruled pass refuses with that text whatever invocation follows the ruled pass; every other refusal is unchanged (card T0-ADVISORY-WITHDRAW R1). In a git repository with a candidate sha recorded and no ruled pass on the candidate, when the candidate's latest R3 decision is an advisory block, `CardRunner.ship` reads the HEAD of the review checkout after the R3 gate and before the merge intent; when HEAD is not the candidate sha it returns a `wait` directive with `on: candidate-moved` and `pollSeconds: 0`, whose narration names both shas, `aidlc card withdraw <id> --cause "<finding>"` and checking out the candidate, and it records no operation, spends no retry and writes no run (R3). A HEAD read that throws ships as before, and so does a candidate whose latest R3 decision is a pass or a merge-blocking block, or that has no decision; a candidate with a ruled pass ships as before whatever invocation follows the ruled pass (no HEAD read, no `candidate-moved` wait).
- `CardRunner.adoptMerge` (`aidlc card adopt-merge <id> --pr <n>`, card T0-ADOPT-EXTERNAL-MERGE-3) records a merge made outside a ship operation, which `applyShipResult` never sees: gh must list PR `<n>` for the card branch into the base and report it MERGED there with a head and a merge commit, and git must find that commit on the fetched base with a tree. One write under the card-run lock, made inside the card lease's `update` section where `ship` records its merge intent, then sets `mergeVerified`, moves the run to CLOSE and removes its stop, a final stop included, with `MERGE_ADOPTED` owed and appended after it; `selectCardState` then selects CLOSE, and the capability blocker of `assess`, a pre-ship check, no longer applies to a merged run, so `card close` and the goal's CLOSE proceed as for a shipped card. It refuses before any write when a gh or git check fails, the card has an intended, issued, running or UNKNOWN operation under any goal (`ship` issues an intended one later outside both locks), or another session holds a live card lease; the last two and a verified merge are checked again inside the lease section. A ship whose gates passed before an adoption committed finds the merge verified in its locked re-read (`shipDrift`) and dispatches nothing.
- The card runner maps outcomes to states: merged -> CLOSE (after merge verification against the token or PR view, else WAIT; a PR view counts only when it is the requested PR, in state OPEN, MERGED or CLOSED, at a named head, and merge facts come only from such a view MERGED at the candidate; card T0-MERGED-VIEW-CHECK), merge-unconfirmed -> CLOSE, STOP/tool or WAIT (a merge token at the candidate first, then gh's PR view; card T0-EXIT-ZERO-NOT-MERGED-3), effect-unknown -> WAIT on the operation (the pool request completed, the run written as WAIT with the result owed, the merge operation `UNKNOWN` with the ship line as its error, the result journaled, no attempt counted; `aidlc ops reconcile` and then `card next` ship again under a new operation; card T0-SHIP-TIMEOUT), review-blocked -> REVIEW_FIX or STOP/review, review-no-verdict -> one retry then STOP/review, ci-red/ci-timeout -> classify then one persisted rerun / BUILD / STOP/ci (the `security` class, keyed off a failing check-run name that matches a secret or security scan or off raw gitleaks output, is STOP/risk and never reruns; a red scan check is no such hit when it failed installing its scanner (cards T0-SCAN-SETUP-STEP and -2): every `[CI-GATE-RED]` and `[CI-GATE-STEP]` line of the text is exactly the line the GitHub ship path prints (`checksJson` or `gateStepLine`: key order, no other or repeated key, no other spacing, a non-empty red array whose elements have no `status` and no `success` conclusion, a step conclusion `failure`, a job id with no leading zero, names in the `encodeUntrusted` encoding) and the text has no `[CI-GATE-TIMEOUT]` line, so one line in another form denies every exemption; exactly one step line names the check, at a failed step on `ci.scanSetupSteps` (default `Install gitleaks (pinned version, checksum verified)`, the install step of the shipped `security-scanners.yml`); it has at most one job record and one gate record, which agree on its conclusion, it is one red check, no red gate line is unresolved, and it is no aggregate wrapper; it is then classified by its other evidence (with none, STOP/ci) and the evidence ends with a `scan-setup:` line, while raw gitleaks output and an unparsed red line naming a scan stay hits of their own; the card runner and `aidlc ci classify --log` read the configured list), dod/verify/scope/budget/red-missing -> BUILD (red-missing reopens a succeeded effort episode), merge-failed with git's or GitHub's own conflict diagnostic on a line of the ship output (from the base sync before the push, the local merge or `gh pr merge`; ## Patterns borrowed

- Anthropic AI-native SDLC playbook: the committed artifact chain (intent.md, spec.md, plan.md, diff, review, deployment, incident), skills as advisory policy and hooks as deterministic gates, control-band monitoring that files findings as intents, continuous evals in CI, REVIEW.md, the production-gate hook.

- specs.md FIRE flow: a single state file as the truth with Markdown views derived from it; resume from the persisted phase, never from artifact existence.
- ai-sdlc-framework: an adapter bag with every side effect injectable (runner, clock, probes) so loops are hermetically testable; definition-of-ready gates as pure functions with `pass|fail|skip`; in-flight tracking backed by on-disk sentinels.
- claude-devops-scaffold: the task-card schema and sentinels, the `verdict.schema.json` contract (case-sensitive `pass|block`, two axes, `run_status`), the ship gate chain and its sentinels, the secret-file deny list, and the guard-frozen hook semantics.
