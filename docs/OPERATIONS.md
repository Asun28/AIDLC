# Operations

How to run goals with the `aidlc` CLI, coordinate sessions, bind provider operations, wire hooks, run evals and audits, and read STOP reasons. Every command below exists in `src/cli/main.ts`; commands print JSON when stdout is not a TTY or when `--json` is given.

## Setup

```bash
npm install
node bin/aidlc.js init [dir] [--cards-dir specs/tasks] [--ship-path scaffold|github|dry-run] [--force] [--dry-run]
node bin/aidlc.js doctor
```

`init` copies `templates/` into the repository: `.claude/skills/aidlc-loop/*`, `.claude/skills/secure-api-review`, `.claude/skills/{tdd,diagnose,grilling,merge-conflicts}` (companion skills), `.claude/agents/*`, a merged `.claude/settings.json`, `REVIEW.md`, `bands.yaml`, `intent/`, `specs/README.md` and `specs/_SPEC-TEMPLATE.md`, `plans/`, `<cardsDir>/_TEMPLATE.md`, `evals/`, `.github/workflows/agent-evals.yml`, `aidlc-ci.yml` and `security-scanners.yml`, `docs/DELIVERY-OPS.md`, `docs/LESSONS.md`, `docs/THIRD-PARTY-NOTICES.md`, `aidlc.config.json`, `aidlc.ops.example.json`, an appended `## AI-native SDLC (aidlc)` section in `CLAUDE.md`, and `.aidlc/` plus `_local/` in `.gitignore`. Existing files are skipped unless `--force`.

`aidlc.config.json` keys (`src/config.ts`): `cardsDir`, `archiveDir`, `intentDir`, `specsDir`, `plansDir`, `evalsDir`, `worktreeRoot`, `base`, `mode` (`local|remote`), `shipPath` (`scaffold` drives `scripts/task.ps1`; `github` runs the native git/gh chain and needs `repository`; `dry-run` for fixtures), `reviewPool`, `reviewPolicyVersion`, `reviewer`, `gateRequired`, `maxWorkers` (1-2), `family` (`claude|gpt`; the Claude role defaults are `claude-opus-5-5`, with `claude-sonnet-5` for the investigator, on the effort ladder low, medium, high, xhigh, max), `provider` (`claude-api|claude-code|mock`; `claude-api` defaults to `claude-opus-5-5` and sends the task's effort as `output_config.effort` on every request), `repository` (`owner/name` for gh), `userLimitMs`, `hooks.frozenPaths`, `hooks.testPathPatterns`, `hooks.productionPatterns`, `tierPaths.tierS|tier0|frozen`, `preReview.command|reviewer|rounds|timeoutMs|onExhausted|shell|maxDiffBytes|answerMarker` (see Pre-review), `formalReview.command|reviewer|timeoutMs|shell|maxDiffBytes|effort|fallback` (see Formal review as a command), `github.requiredChecks|requireVerdict|ciTimeoutMs|ciPollMs` (see Ship gates).

`worktreeRoot` is the directory card worktrees are created under, joined with the card id (`resolveWorktreeRoot`, `src/config.ts`). Empty resolves to a root scoped to the repository: `%SystemDrive%\wt\<name>` on Windows and `$HOME/.wt/<name>` elsewhere, where `<name>` is the base name of the main checkout (`C:\wt\AIDLC` for a checkout at `D:\Projects\AIDLC`), so two repositories with a card of the same id never share one directory. An explicit value is used as given (this repository sets `D:\wt\AIDLC`); the installed template leaves it empty so a downstream repository keeps that default until it sets one. A checkout at a filesystem root (`D:\`, `/`) has no name to scope by and must set `worktreeRoot`: the resolver throws, naming the checkout and the key, rather than fall back to the unscoped root. A `SystemDrive` or `HOME` set to the empty string counts as missing (`C:`, `/tmp`), never a relative root. Before this rule the empty default was the unscoped `%SystemDrive%\wt` or `$HOME/.wt`. A repository whose card worktrees still sit there is not searched: its next PREPARE stops with the ownership message `worktree for <id> is at <old root>\<id>, expected <old root>\<name>\<id>`. Either set `worktreeRoot` to the old root or move the worktrees (`git worktree move`, or remove and re-add them on Windows across drives) before running the card again.

## Running a goal

### T0 bugfix

```bash
aidlc goal new "NPE in ClaimStatus when adjuster is null" --bug-evidence
aidlc next                                  # plan (T0-bugfix: one coherent card, no funnel)
# write specs/tasks/T0-CLAIM-NPE.md (diagnosis + fix + regression test), then:
aidlc cards validate --card T0-CLAIM-NPE
aidlc report --result cards-projected --cards T0-CLAIM-NPE
aidlc next                                  # run-card T0-CLAIM-NPE
aidlc card fix-task T0-CLAIM-NPE            # locks test files for the agent (protect-tests hook)
aidlc card next T0-CLAIM-NPE                # prepare -> build
# establish RED, implement, run the DoD, then:
aidlc card attempt T0-CLAIM-NPE --outcome success --dod-receipt "pytest exit 0" --red-receipt "<sha>:1"
aidlc card fix-task --clear
aidlc card next T0-CLAIM-NPE                # ship (dry-run or scaffold task.ps1)
aidlc card next T0-CLAIM-NPE                # close: lists missing closure steps
aidlc card close T0-CLAIM-NPE --all         # the five mechanical steps; the lesson step stays open
aidlc card close T0-CLAIM-NPE --lesson "NEVER <rule> (source: <ref>)"   # or --skip-lesson "<why>" (commander reserves --no-)
aidlc next                                  # verify-arc, then report arc-verified
aidlc report --result arc-verified --detail "regression test green on integrated SHA"
aidlc next                                  # close -> done
```

A success attempt on a `tdd: true` card is refused when neither the stored run nor the attempt carries a RED receipt: `aidlc card attempt` names the missing RED receipt and records nothing (no attempt, no effort change, no candidate), so record the success again with `--red-receipt`. A failed attempt is recorded with `--outcome fail --cause "<normalised cause>" [--progress]`; the same cause twice without progress stops the branch, and only an evidenced third failure can justify the single escalated attempt.

### T1 feature

```bash
aidlc intent new --title "Claims status self-service" --author "J. Ortiz" --problem "..." --outcome "..." --affected "..." --constraints "..."
aidlc intent validate intent/claims-status-self-service.md
aidlc spec validate specs/claims-status.md
aidlc goal new "add claims status self-service to the portal" --intent intent/claims-status-self-service.md    # routes T1; PLAN lists the open questions of the intent and names the grilling skill
aidlc next                                  # plan: concise plan points and 2-5 cards
aidlc plan check plans/claims-status.md     # definition-of-ready gates
aidlc report --result plan-produced --plan-ref plans/claims-status.md
aidlc cards project --plan plans/claims-status.md --write   # drafts from the task-split table; edit before validate
aidlc cards validate
aidlc report --result cards-projected --cards T1-STATUS-API,T1-STATUS-PANEL,T1-STATUS-NAV
aidlc next                                  # run-card for the first wave (cap two, disjoint resources)
```

Repeat `aidlc card next <id>` per dispatched card. When every card is DONE, `aidlc next` returns `verify-arc`; report `arc-verified` with evidence, or `aidlc goal repair <goal> --cards T1-STATUS-FIX --detail "..."` for the single bounded repair cycle.

### T2 system

Same as T1 with the full funnel. After `cards-projected`, `aidlc next` returns `checkpoint` with the plan+projection packet. Approve once with `aidlc plan approve <goalId> --by <who>` (or `aidlc report --result approved --kind plan-checkpoint`); approval is carried forward for the same revision. `aidlc goal amend <id> --text "..." [--cards ...] [--replace '{"T2-OLD":"T2-NEW"}']` records a revision and returns to PLAN with unaffected evidence retained.

### Standalone release (package / staging / production)

```bash
aidlc goal new "package a runnable build of the portal" --target package
aidlc next                                  # release directive with attemptId (goal is in DELIVER)
aidlc release candidate <attemptId> --digest <candidateDigest> --sha <sourceSha> [--env staging] [--config-digest <d>]
aidlc release next <attemptId>              # prepare: needs, or NOT CONFIGURED -> STOP/release-config
aidlc release report <attemptId> --step package-run-proof --status succeeded --evidence "installed and ran smoke"
```

Staging: `--target staging`; `release next` issues the bound `deploy` operation for the staging environment, waits on provider status, then asks for `stage-verify` (`aidlc release report <id> --step stage-verify --status succeeded`). The attempt finishes after staging verification; CHECKPOINT/APPLY are never entered.

Production: `--target production`; after staging verification `release next` prints the approval packet (`aidlc release packet <id>`). Record the authority bound to the exact candidate, environment and operations:

```bash
aidlc authorize production --goal <goalId> --env production --candidate <digest> --sha <sourceSha> --ops deploy,status,health --by "release manager" --ref CHG-1234
aidlc release next <attemptId>              # apply -> observe (health window) -> close -> done
```

Without `--by`, `aidlc authorize`, `aidlc plan approve` and `aidlc report --result approved` record the git identity of the repository as the approver (`git config user.email`, else `user.name`), and `user` when neither is set; no other command reads the git identity.

A BREACH routes to RECOVER only with a `recovery` authorization (`aidlc authorize recovery --env production --ops rollback --recovery '{"eligibleBaseline":"v1.4.2","healthTrigger":"5xx>2%","procedure":"rollback","migrationCompatibility":"expand-only","windowMs":1800000,"owner":"oncall"}'`); the attempt closes as `recovered`, and the goal stops with `release-health` so a new candidate re-enters with fresh approval.

### Incident -> intent

```bash
aidlc monitor check --bands bands.yaml --data samples.json --file-intent
```

`samples.json` is `{"baseline":[...numbers...],"recent":[{"at":"<iso>","value":n},...]}`. Deterministic Western Electric rules decide the tier; `diagnose`/`propose` breaches file `intent/incident-<metric>-<rule>-<date>.md` once per dedupe window and record the identity in `.aidlc/incidents/incidents.json`. The intent then enters the normal loop with `aidlc goal new`.

## Sessions

- Every process identifies its session: `AIDLC_SESSION` when set (one value per window, the explicit override), else the Claude Code session, which Claude Code exports to its Bash and PowerShell subprocesses as `CLAUDE_CODE_SESSION_ID` (the older `CLAUDE_SESSION_ID` is still read), else the default token in `.aidlc/session-default`, which every process without a session shares, so lease ownership cannot tell windows apart; `aidlc doctor` prints the source, and `DEFAULT: every window shares this identity` in that case. A hook process acts as the `session_id` of the hook event, the same Claude Code session. A `/clear` or a new window is a new session, and a lease recorded under the default token by an earlier version belongs to that token; no lease record is rewritten. `aidlc goal takeover <id>` takes the goal lease once it has expired (10-minute TTL) and the old owner's operations are reconciled; it does not touch card leases. A card whose lease is held by an ended session stops for ownership: a fresh run at PREPARE, naming the owner and the takeover command; a run in progress before PREPARE, with the generic stale-generation detail. That stop outlives the lease's expiry. `aidlc card status <card> --goal <id>` prints the lease next to the run (`lease.owner.session` and host, `lease.generation`, expiry, released, whether this session owns it) and the run's `ownerGeneration`, live or expired. While the lease is live the only continuation is the owner identity: when `ownerGeneration` equals `lease.generation`, which holds for every run PREPARE completed, run with `AIDLC_SESSION=<lease.owner.session>` on the same host and the renewal clears the stop (a run interrupted between the lease claim and the end of PREPARE has no `ownerGeneration` and is not continued this way). Once the lease has expired and no operation of the card is unresolved in any goal that lists it (the lease is one resource per repository and card; `aidlc ops list --goal <id>` shows each goal's, and the takeover names the ids it finds), `aidlc card takeover <card> --goal <id>` takes it in the acting session: the lease generation advances (a write of the old owner at its generation is fenced), the run, read again once the lease is held so that a stop another process persisted meanwhile stays, records the new generation, a run without one included, and the card state is selected again from the persisted evidence, which clears the ownership stop and keeps any other stop as `card next` would (a deadline the wall clock has passed selects STOP/time, the case `aidlc goal extend` re-admits once the dispatch has stopped the goal on it); `aidlc card next <card>` then continues the card, a run without a worktree at PREPARE. The takeover refuses and writes nothing when the card has no lease record or a released one (`card next` claims those: an ownership stop whose lease is absent or released is lifted by `card next`, never one whose lease has merely expired), when this session holds the lease at the generation the run carries (`card next` renews it), while the lease of another session is live (expiry alone does not prove the owner stopped) and while an operation of the card is unresolved in any goal (named by id; `aidlc ops reconcile` first); the record and the ledger are read again inside the reconciliation, so a release, a takeover or an operation that landed after the command's first read is seen. An operation admitted after that read and before the lease write is found right after the write: the lease stays taken (its writer is fenced from then on), the run stays as it was, the command names the ids, and once they are reconciled the command run again completes the takeover. A handoff intent is journaled before the lease write (`NOTE`, `card-takeover-intent`, naming the previous owner and bound to the acquiring session and the acquisition time the lease will carry, so an intent whose write never landed matches no lease) and one `LEASE_ACQUIRED` per generation after it, whatever journaled it (PREPARE's claim journals one before it saves the generation), both resolved by card resource and generation in every goal's journal, so a process that ends in between leaves a completion that names the previous owner and journals the completion (`NOTE`, `card-takeover-completed`) rather than a second acquisition. Every hint the command prints names the goal it ran under. A lease this session holds at a generation the run does not carry is such a takeover (or a claim) whose run update did not land: running the command again completes it without another advance, after reading the lease once more (a record released or taken by another session since the first read refuses without a write), and refuses while an operation of the card is unresolved. `card next` reads the stored run, never a caller's snapshot, before its plan-checkpoint guard too: a dispatch from a window that kept the run it read before the takeover records only its ownership stop on the stored run (which the owner's next call clears), writes nothing of its own back, and a stop already persisted there (risk, time) stands. The guarantees end where the store's do: `.aidlc/` writes are atomic but have no compare-and-set, so four windows remain, each with its recovery. The lease write: a renewal by the old owner that lands between the lease store's read and its write is overwritten (the primitive's window, shared with `aidlc goal takeover`), and the old owner's next write is fenced. The run write: every run writer of the runner (`next`, `recordAttempt`, `ciReconcile`, the ship, the reviews, the closure) saves onto the stored run it re-reads, so none writes a generation or a stop it read earlier back; the ship and the reviews fence at that run's generation before they save, and one that passed its fence before the lease write and saves after it writes the run at the old generation; `recordAttempt` applies no fence at all, so a delayed attempt record of the old owner lands its receipts and candidate on the stored run (not its generation or a persisted stop), and a raw `card report` patch is unfenced as well; the takeover's own save can lose a stop persisted after its read. `aidlc card takeover` run again completes a run left at the old generation, and a lost stop is re-recorded by its author. The journal: two completions of one session may both journal the acquisition of one generation; the audit keys on generation. The ledger: an operation admitted after the takeover's last read is left to the assessment of `card next` (issued, running and UNKNOWN in the run's goal, as always); an intended one is reconciled with `aidlc ops reconcile`. The goal lease is untouched, and the goal-level `aidlc next` run between the card's stop and the takeover stops the goal on that stop: `aidlc goal resume <id> --reason "<why>"` after the takeover, and the dispatch then reports the card running (`wait` on `<card>:BUILD` for a run with a worktree, `run-card` for one at PREPARE) until `aidlc card next <card>` continues it.
- `aidlc goal status`, `aidlc goal list`, `aidlc board [goalId]` show state; the board is a view.
- Planning claims (card T0-PLANNING-CLAIMS): planning artifacts (intent, spec, plan, card files) are drafted on the main checkout before a goal reaches RUN, so a second window in the same checkout sees them only as untracked or modified files. Which goal owns each one is derived from the goal record and its lease, never from a claims file or a second lock: a non-terminal goal claims its `intentRef` and its `planRef` (each when it lies under one of the four planning directories), the spec and plan of the intent's slug (`<specsDir>/<slug>.md`, `<plansDir>/<slug>.md`), and the card file of every card it lists or its plan's task split names; a terminal goal claims nothing; a path two goals claim keeps the older goal by its `createdAt` instant, then id (`src/state/claims.ts`). Two surfaces show it. `aidlc doctor` prints `workingTree`: `clean`, or one entry per uncommitted file under the four planning directories, `"<path>": claimed by <goal> (session <id>, lease live until <T>|expired at <T>|released)`, `(no lease)` for a goal that has not been coordinated yet, `(lease unreadable: <code>)` for a lease record that cannot be read, or `"<path>": unclaimed`; the path is JSON-quoted, and so is a goal or session id that is not a plain identifier (letters, digits, `.`, `_`, `:`, `-`), so a name is data on its line (`n/a` outside a git repository; `UNREADABLE: git status failed (exit <n>|UNREADABLE)` when the status cannot be read, the probe's exit code and never git's text; goal records that cannot be read leave every entry `claim unknown (goal records unreadable: <code>)`, the code one of the store's read codes or `UNREADABLE`, never the error text, which may quote the record; a plan that cannot be read names no extra cards for its goal alone, its goal's entries carry `; plan unreadable: <code>`, and an unclaimed file under the cards directory is then `claim unknown (plan of <goal> unreadable: <code>)` since that plan may name it; every porcelain entry counts, untracked, modified, added, renamed (both endpoints: the source is a staged deletion), copied (the destination) or deleted, each pathname read on its own and a C-quoted one decoded, the arrow read only from an R or C status column; nothing throws out of the entry check). Every reference and configured directory is checkout-relative (forward slashes, dot segments resolved, the absolute and drive checks repeated after normalisation; a backslash is a separator only on Windows and never in a git path): an absolute or escaping reference, or one outside every planning directory, is neither read nor claimed, and a card id maps to `<cardsDir>/<id>.md` only when that canonical path stays under the cards directory. The report is `workingTreeReport` in `src/state/claims.ts`, every read injected. The Stop hook (`verify-before-done`) adds `[aidlc] Planning artifacts of goal <id> are uncommitted on main: <files>. Commit them before the session ends; another session sees only files it does not own.` for each goal whose lease the acting session holds on this host (expiry is not consulted, as for card leases) and whose claimed files are uncommitted, each file JSON-quoted and the goal id JSON-quoted when it is not a plain identifier, so a name never forms a second instruction, in the same Stop message as the DoD context; another goal's unreadable plan takes nothing from this goal's reminder, and a card-run record that cannot be read ends the DoD check alone; when the planning check itself cannot run (git, config or a store read) the hook adds `[aidlc] The planning-artifacts check did not run (<code>); ...` instead; a goal whose lease another session holds, a released lease, a goal without a lease, a terminal goal, a checkout that is not a git repository and a repository without a state directory add nothing. The rule for a session: leave another goal's file alone; commit your own goal's planning artifacts on main as soon as they validate and before you stop (`aidlc-loop` entry check 1).
- A second window that runs `aidlc next` on a goal owned by another live session receives `wait` with the owner and lease expiry. After expiry, `aidlc goal takeover <id>` succeeds only when `aidlc ops list --goal <id>` shows no unresolved operations; otherwise reconcile first with `aidlc ops reconcile <opId> --status succeeded|failed|running|cancelled|UNKNOWN`.
- `aidlc review status [--pool <name>]` shows active slots, queued requests, `retry-after` holds and the pool reset time. Raising a pool above one concurrent review needs provider evidence (`ReviewQueue.setPoolLimit`).
- `aidlc goal extend <id> --until <iso> --by <who> --reason "..."` is the only way to move a deadline; retries, revisions and delayed approvals never extend it. An extension (an ISO-8601 UTC timestamp) re-admits a goal stopped for time and every card of its current projection stopped for time (their deadlines move to the new goal deadline, the runs are in progress again; a stop for any other reason, or of a card superseded by a revision, stays); re-entry runs through the projection check, so a T2 goal is re-authorized before any dispatch. `aidlc goal resume <id> --reason "..." [--text "..."] [--cards a,b] [--replace '{"old":"new"}']` carries a revision into the resume (replacement ids must exist in the registry, a superseded card may not stay listed, and a listed card keeps every prerequisite it names) and applies it before the projection, re-entering through CARDS with the completion evidence of the old projection invalidated, the only way to re-plan a terminal goal (a DONE goal included): `aidlc goal amend` refuses a terminal goal and names the resume.
- `aidlc goal cancel <id>` and `aidlc goal resume <id> --reason "..."` handle terminal goals; resume links a new generation and keeps exhausted limits.

## Provider operation bindings

`aidlc.ops.json` (schema `DeliveryOpsConfig` in `src/delivery/ops.ts`; example in `aidlc.ops.example.json`):

```json
{
  "schemaVersion": 1,
  "environments": {
    "staging": { "description": "pre-production", "production": false },
    "production": { "description": "live", "database": "claims-prod", "production": true }
  },
  "operations": [
    { "role": "deploy", "command": ["./scripts/deploy.sh"], "targetSelection": "arg", "targetArg": "--env",
      "async": true, "operationIdPattern": "deployment id: ([A-Za-z0-9-]+)",
      "statusLookup": ["./scripts/deploy-status.sh", "{id}"], "successPattern": "status: healthy", "failurePattern": "status: failed",
      "idempotencyKeyArg": "--idempotency-key", "timeoutMs": 1800000, "effects": ["replace running version"], "credentialScope": "deploy-role" },
    { "role": "status", "command": ["./scripts/deploy-status.sh"], "targetSelection": "arg", "targetArg": "--env", "externallyVisible": false },
    { "role": "environment", "command": ["./scripts/env-identity.sh"], "targetSelection": "arg", "targetArg": "--env", "externallyVisible": false },
    { "role": "health", "command": ["./scripts/health.sh"], "targetSelection": "arg", "targetArg": "--env", "externallyVisible": false },
    { "role": "recover", "command": ["./scripts/rollback.sh"], "targetSelection": "arg", "targetArg": "--env", "async": true,
      "statusLookup": ["./scripts/deploy-status.sh", "{id}"], "successPattern": "status: healthy", "effects": ["restore previous version"] }
  ],
  "health": [
    { "name": "http_5xx_rate", "source": "prometheus", "threshold": { "op": "<", "value": 0.02 }, "minSamples": 30, "maxStalenessMs": 120000, "windowMs": 600000, "maxWaitMs": 1800000, "owner": "oncall" }
  ]
}
```

Rules: commands are argv arrays, never shell strings; `async: true` means exit zero is only "issued" and the outcome comes from `statusLookup`; `triggersPublication: true` puts the operation behind production authority; `aidlc release ops --target staging|production|package|migration` lists which roles are bound and which are `NOT CONFIGURED`. Required roles: package -> build, package; staging -> deploy, status, environment, health; production -> those plus recover; migration -> migration-status, migration-apply, backup-verify. An unreadable config is a failure, never "off".

## Hooks

One hook process per event. `templates/claude/settings.json` (merged by `init`) wires a single command for `PreToolUse` (matcher `Bash|Edit|Write|MultiEdit`), `Stop` and `UserPromptSubmit`; that process runs every guard that applies to the event (`src/hooks/entry.ts`, `dispatchHook`) and returns the first block, else the first advisory output. `init` picks the fastest entry it can see: `node node_modules/aidlc/bin/aidlc-hook.js` when the package is installed locally, `node bin/aidlc-hook.js` inside the aidlc repository itself, otherwise the portable `npx --no-install aidlc hook auto`. Both bin entries load the compiled build only when it is at least as new as every file under `src/` (`bin/resolve-entry.js`: reasons `dist`, `no-dist`, `stale-dist`, and `src-unreadable` when a source below a readable `src/` cannot be inspected, since an incomplete scan is never proof of freshness; links to files and directories are followed; `AIDLC_ENTRY_DEBUG=1` prints the choice to stderr), so a checkout with a build from an earlier commit runs the sources, never the stale build. Measured on Windows: about 0.2 s per tool call for the direct entry, about 1.4 s for the npx form, against about 4.5 s for the 0.1.0 wiring that started three npx processes per tool call. Re-running `aidlc init` on a repository with the 0.1.0 per-guard hooks replaces them with the dispatcher and keeps any foreign hooks. `aidlc hook <name>` still runs one guard for debugging.

| Guard | Runs on | Blocks when |
|---|---|---|
| `production-gate` | PreToolUse Bash | the command matches a deploy/release verb together with `prod|production|live` and `RELEASE_APPROVAL` (or `AIDLC_RELEASE_APPROVAL`) is unset or does not name a recorded production authorization; exit 2 with the reason |
| `protect-paths` | PreToolUse Edit, Write, MultiEdit, Bash | the file path or a write-verb command matches `hooks.frozenPaths`; a read-only command is deferred with a note |
| `secrets-guard` | PreToolUse Edit, Write, MultiEdit, Bash | content looks like a credential (Anthropic, OpenAI, AWS, GitHub, Slack keys, private keys, inline password assignments) or the target is a secret file (`.env` except `.env.example`, `.pem`, `.key`, `id_rsa`, `.secrets/`) |
| `protect-tests` | PreToolUse Edit, Write, MultiEdit | a fix-task marker is active (`AIDLC_FIX_TASK` or `.aidlc/fix-task`) and the path matches `hooks.testPathPatterns` |
| `verify-before-done` | Stop | never blocks; adds context when an active card run in BUILD, SHIP or REVIEW_FIX has no DoD receipt and its card lease is absent, released or owned by the acting session (the hook event's `session_id`, or `AIDLC_SESSION`); a run whose lease names another session is that session's to verify; a lease record that cannot be read leaves its run listed for every session and is named by card id and store error code only, never by content; adds Stop context asking for the verification output; and, in the same message, when a goal whose lease the acting session holds has uncommitted planning artifacts on main (Sessions, Planning claims) |
| `route-new-work` | UserPromptSubmit | never blocks; prints the `[route]` line and size guidance for build/fix/deploy requests |

The scaffold's 18 secret-file `Read(...)` denials are merged into `permissions.deny`.

## Pre-review (R2)

A bounded second-model review in front of the ship, so the formal PR review (R3, two substantive decisions) sees candidates that already passed a cheaper review. Configure it in `aidlc.config.json`:

```json
"preReview": { "command": ["deepseek", "--model", "deepseek-v4-pro"], "reviewer": "deepseek-v4-pro", "rounds": 3, "timeoutMs": 600000, "onExhausted": "stop" }
```

`command` is argv (the prompt arrives on stdin; on Windows it runs through a shell unless `shell` is set); an empty command disables the stage. `aidlc review pre <card>` builds the prompt from `REVIEW.md`, the card (acceptance, allow_paths, non_goals, forbid, tier, diagnosis), the committed diff against the base and the run's unresolved findings with their dispositions (see Findings and dispositions), runs the command with a receipt, takes the last top-level JSON document of the whole output as the verdict (one string-aware pass over the output: outside a document only a JSON-looking opener starts one, a brace followed by a key or a closing brace with whitespace before the first key unbounded, or a bracket followed by an object, a string or an array; a brace followed by nothing but whitespace to the end is a document cut short; inside a document strings and escapes are tracked, so a brace or bracket in a quoted reason opens nothing, and brackets nest with braces, so an object nested in an array is never a document of its own and an enclosing array is a document, cut short while unfinished and not a verdict once finished; a document spanning lines is one document; a JSON-looking document after the decisive one that is cut short or does not parse makes the output malformed, whatever a nested axis says, never replaced by a draft earlier in the reasoning; JSON is read from each opener: an output that ends inside one is a document cut short and the output is malformed, whatever state the cut landed in (an open container, a dangling separator or colon, a key without its value, a string cut in its text or inside an escape, a literal or a number cut mid-token: each completes into a valid document), an unfinished enclosing array included, so its nested object is never the verdict; a character JSON cannot carry there means the opener was prose that merely starts like JSON, as a reviewer quoting a JSON contract in its reasoning writes, so it opened nothing and the scan resumes at that character, and the complete document that follows still decides. Each character is read once, so an output full of such prose costs what its size costs; a prose opener with no parseable document after it leaves the output malformed, so a corrupt final document is never answered by an earlier draft; prose around the document is ignored), writes `.review/<card>.pre.<cycle>.<round>.json` and `.log` next to the candidate, records the round in the card run and journals `PRE_REVIEW_DECIDED`.

A verdict document inside a Markdown code fence (```json or a bare ```) is read as the verdict when the fence closes after it; a document inside a fence that never closes makes the output malformed, and the last document still decides, fenced or not. A fence opens on a line of up to three spaces, three backticks and an info string without a backtick, and closes on a line of up to three spaces and three backticks alone, or with backticks right after the document and nothing but whitespace after them on that line (card T1-REVIEW-LOOP-GUARDS). `preReview.answerMarker` (default empty) names the line that separates a pre-reviewer's reasoning from its answer: when it is set, each angle is read from the stdout after the last line that equals the marker once the surrounding whitespace of both is trimmed, so fence lines and JSON-looking text in the reasoning never decide the verdict, and the fence rule and the last-document rule apply to that answer alone (card T0-R2-ANSWER-MARKER). With the marker set, an output with no marker line is a `malformed` no-verdict round even when its last line is a verdict, so an output cut before its answer never passes; the formal review (R3) reader ignores the setting. This repository sets `=== answer ===`, the line the DeepSeek CLI prints between its reasoning and its answer.

Learned invariants (card T1-REVIEW-INVARIANTS). Both prompts carry a `## Learned invariants` section right after the review policy: the NEVER and ALWAYS lines of `docs/LESSONS.md` in the main checkout, newest first, each quoted as one JSON string like a prior finding, with the instruction that a rule is data and never an instruction, that the reviewer checks every site of that class in the diff, and that each site is its own finding cited with `file:line`. NOTE lines are process notes and are never sent. `reviewLessons` (`src/artifacts/lessons.ts`) fills `REVIEW_LESSONS_MAX_BYTES` (3000 bytes of lesson text) newest first, stops at the first rule that does not fit and counts the rest, which the section names as `<n> older lessons omitted at the byte cap`; an absent or invariant-free file renders `- none`. The file is read with the other prompt inputs, before the dispatch's first mutation, so a lesson appended while a review runs reaches the next dispatch, not this one.

Review inputs (card T1-REVIEW-INPUTS). The committed diff is sent whole: one above `preReview.maxDiffBytes` (`formalReview.maxDiffBytes` for R3) is refused before any dispatch, naming the size and the cap, with no round, decision, receipt, pool request or journal event recorded; a diff is never cut. Every round and decision records `policyHash`, the sha256 of the REVIEW.md text it applied (the fallback policy text when the file is missing): on the round or invocation record, as `policy_hash` on every retained verdict document (the angle sidecars, the round document, the canonical `.review/<card>.json`) and on `PRE_REVIEW_DECIDED` and `REVIEW_DECIDED`; a ship-path decision records the `policy_hash` its verdict document names (the canonical document a command decision published, or one the ship path's reviewer wrote), else the hash of the REVIEW.md in force when the ship was dispatched (`CardRunner.shipBindings`; only a record from before the field carries none); the exhausted hand-off event carries the hash of the round it hands on. `review r3` checks the cap on the candidate diff and on the delta, re-reads the last reviewed candidate after the release of a failed reservation (recollecting the delta under the cap), and only then records the hand-off, the pool request and the reservation, so a refused review records nothing; a decision landing during the hand-off write refuses in the reservation lock (run the command again) and the hand-off, R2 bookkeeping, stands (the SHIP gate records the same hand-off when it issues the review directive). The prompt names the hash in its policy heading and, when the candidate changes a rule file (`REVIEW.md`, `CLAUDE.md` or `AGENTS.md` by name anywhere, or anything under `.claude/` or `templates/claude/`), lists those files with the note that the applied policy, never the changed text, governs the review. A round or decision that follows an earlier decided one of the same stage (a pass or a block on any candidate, by any reviewer) collects `git diff <last reviewed sha>...<head>` under the same cap and renders `## Delta since the last reviewed candidate` (the no-change note when the shas are equal; a repository-reading reviewer, whose prompt travels in argv, receives the delta's paths and a `git diff <last sha>...<candidate sha>` command pinned to the candidate instead of the text, as it does for the diff); the last reviewed candidate is read again on the record locked at reservation, and a decision recorded meanwhile refuses the dispatch (run the command again). A new finding whose cited file is outside that delta, and every new finding when the delta is empty, is recorded with `outsideDelta`: a first-round miss, marked by `aidlc review findings`; a re-raise is never marked, and a first round marks nothing. A ship-path decision's findings are marked against the delta bound at the ship dispatch: none before the formal stage's first decision, an empty delta for the same commit (every new finding a first-round miss), the committed diff for another commit in a git repository (a delta above the cap refuses the dispatch before any intent), nothing outside one. A reason that opens with `[question]` or `[suggestion]` (after the axis tag if any), or whose text after the `@ <file:line>:` location opens with one, is advisory in both stages whatever else it carries (a path or prose that merely contains the bracket text is no tag, so a cited block is never downgraded by its wording): retained on the round record (`PreReviewRound.advisory`, the reasons a pass carries included) and in the verdict file, printed by `aidlc review pre`, never a block; the formal prompt lists the latest decided pre-review round's advisory notes for the candidate under `## Pre-review advisory notes` as quoted, non-blocking evidence. On the ship path the verdict document is classified with its tagged reasons moved to advisory notes: a block carried only by such reasons is a pass with the notes (no block consumed, the notes on `REVIEW_DECIDED`), and when the ship path itself refused the merge on that document the card stops for a human (STOP/review naming the notes) with its candidate and DoD receipt kept: no repair is asked, no decision or block consumed. `reviewPolicyVersion` is `REVIEW.md@3` in both configs; a pass recorded under the earlier version stays valid for its candidate only.

The gate lives inside SHIP: `aidlc card next` returns a `pre-review` directive until a `pass` exists for the current candidate. A `block` moves the run back to BUILD (the DoD receipt is cleared; the reasons are carried into the next prompt) and reopens the effort episode without spending an attempt: the rounds are the pre-review's own budget, and the effort ladder (baseline + 2 repairs + 1 justified escalation) counts DoD failures only. Rounds are capped per R3 cycle by `rounds`; a third block with `onExhausted: "stop"` is STOP/review with the retained verdicts, `"ship"` hands the residual findings to R3 instead. A missing or malformed verdict gets one retry, a reported quota hold is retried after the hold and never counts as a decision. An R3 block starts a new cycle: the repaired candidate needs a fresh pre-review pass before it ships again. R3 itself (`reviewer`, `gateRequired`, the PR review) is unchanged.

A review whose process returns no verdict that counts (none was read, or the process did not exit 0) is a quota hold only on a quota message: from a process that exited 0, in its stderr alone, since its stdout is its answer and the reasoning there can name a quota word; from any other process (a non-zero exit, or no exit code after a signal), in its stdout or its stderr. For a review command (R2, and R3 run by `aidlc review r3`), a process that timed out is a `timeout` no-verdict round and never a hold, and without a quota message the round is a no-verdict round: `tool_error` for a process that did not exit 0, `malformed` for one that exited 0 with text on stdout, `no_output` for one without. The ship path reads the receipt of its ship command by the same stream rule, and records a missing verdict without a quota message as `malformed`. Each quota pattern matches in any letter case and only as a whole word: `quota` or `quotas`, `429` or `429s`, `too many requests`, `rate limit` (also `rate-limit` or `ratelimit`, and with `s`, `ed`, `er` or `ing`), `usage limit` or `usage limits`, `retry after` or `retry-after`, `capacity` and `overloaded`. A word ends at the start or end of the text, at any character other than a letter or digit, at a change from a lowercase to an uppercase letter, and before the last capital of a run of capitals that a lowercase letter follows; `_` and those two case changes also separate the words of a phrase, so `insufficient_quota`, `RATE_LIMIT_EXCEEDED`, `rateLimitExceeded`, `RateLimitError`, `QuotaExceeded` and `APIQuotaExceeded` hold; any other letter or digit next to the word joins it, so `Quotation`, `4290`, `HTTP429`, `E429`, a sha containing `429` and a compound written in one letter case such as `quotaexceeded` or `XQUOTA` never hold (card T0-QUOTA-FALSE-HOLD-2). The same separators make `retryAfter`, `tooManyRequests`, `usageLimit` and the `_` forms such as `rate_limit` and `too_many_requests` hold, which no pattern matched before that card. A `review-no-verdict` ship outcome whose receipt carries a quota message is a quota hold on the ship path as well: the ship returns a `wait` directive on `review-quota`, holds the review pool for 15 minutes, leaves the card out of STOP and spends neither the no-verdict retry nor a substantive decision (card T0-SHIP-QUOTA-WAIT-3). While the hold stands, `aidlc card next` waits on the held pool and ships nothing; once it has passed, `aidlc card next` ships the same candidate again, and the hold never extends the card deadline. Only a `review-no-verdict` ship outcome holds the review pool on a quota message (card T0-SHIP-HOLD-OUTCOME): the receipt of the ship path is the output of the whole ship command (git, gh and the CI gate log), not only of its reviewer, so a ship that merged, whose CI gate failed or that ended with any other outcome settles its pool request without a hold (the request is completed, or marked lost when the ship timed out), sets no pool `resetAt` and journals no `REVIEW_HOLD`, whatever quota message its receipt carries. A hold set by such a ship left its request in `retry-after` after the card had closed; once the hold passed, the pool admitted that request as running, and nothing completed it.

Acceptance coverage in shadow (card T1-REVIEW-COVERAGE). `preReview.coverage` is `off` (the default, and what `aidlc init` installs) or `shadow`; this repository runs `shadow`. In shadow the `ac-coverage` angle of a pre-review round, and nothing else, is asked for one entry per numbered acceptance item: its contract line gains `"coverage":[{"item":1,"status":"supported|violated|unknown","impl":"file:line","test":"file:line"}]` and its angle text asks for one entry per item and says the list never changes the verdict. Every other angle, the single-pass prompt and the R3 prompt are the prompts `off` builds, byte for byte (pinned in the tests by the hashes of the pre-change prompts), and `shadow` with a `{schema}` pre-review command is refused by the configuration parser: the frozen `VERDICT_SCHEMA` a `{schema}` reviewer is pinned to has no such field. A panel without the `ac-coverage` angle asks for nothing and records nothing, and so does the deterministic scope-gate block, which runs no reviewer.

The request is also what the retention obeys: a coverage list is kept, joined and written only for the angle that was asked. A reviewer that volunteers one in `off`, any other angle of a shadow panel, and every formal (R3) reviewer are retained exactly as they were before the setting existed, list dropped. Because one angle is asked today, a round's `conflicted` list is empty in practice; the join labels several angles because `joinCoverage` is the contract, not because the panel asks more than one.

`joinCoverage` (`src/review/pre-review.ts`) joins what each angle reported, not what its classification left: an angle whose verdict is dropped because its axes contradict it, or rewritten by the citation rule, still contributes its entries and its rejected-entry count, and the round's outcome is untouched by any of it. It joins the entries per item once the round has decided: an item at least one angle reported a well-formed entry for is accounted, one no angle reported is `unaccounted`, one angle supported and another violated is `conflicted`, and an item a passing angle marked violated is `inconsistent`. That last check reads the verdict the reviewer reported, not the one the citation rule left: a block carried only by uncited reasons is classified as a pass, and an angle that reported a block is consistent with its own violated item. `supported` without both the implementation and the test named is the angle not having verified it, so it joins as `unknown` and still accounts for the item. `malformed` counts every entry that joined nothing: an item outside `1..expected` at either bound, every entry of an item one angle reported twice (counting the items named by rejected entries too, however they were written, any numeric string whose value is the item included (`"1"`, `"1.0"`, `"1e0"`), while a string that is no number or no integer names none, so a repeat is never hidden behind a twin the shape threw away), and the entries the verdict parser rejected because they do not satisfy the bounded shape (`{ item: positive integer, status: supported|violated|unknown, impl?, test? }`), which are counted at the parse and carried into the round rather than dropped. `angles` lists the angles that reported a list at all, so an angle that ignored the request is absent and its items fall to `unaccounted`, which is the measurement shadow exists for.

The result is retained and read by nothing: `PreReviewRound.coverage` on the round record, `coverage` on the `PRE_REVIEW_DECIDED` event and on the aggregated round document under `.review/` (a round that asked for coverage always writes that document, a single-angle panel included, and keeps the angle's own file beside it), and one line in the `aidlc review pre` summary, `coverage: <accounted>/<expected> accounted` followed by the unaccounted, conflicted and inconsistent item numbers when there are any. The round's outcome, its findings, the reasons, the R3 prompt and every allowance are what they are with `coverage: off`; rounds recorded before the setting existed, and every round in `off`, carry no coverage at all.

### Review panel

With `preReview.perspectives` set, one pre-review round runs one reviewer process per perspective concurrently, each with a perspective section in its prompt (built-in guidance for `bugs`, `security` and `compliance`, the three passes in REVIEW.md; any other name is a custom focus). The round verdict is aggregated: quota-hold > block > no-verdict > pass, so a round passes only when every angle passes; block reasons are unioned and tagged with their perspective; axes take the worse verdict; angles that bind different candidates never aggregate into a pass. Per-perspective verdict and log files are retained as `.review/<card>.pre.<cycle>.<round>.<perspective>.*` next to the aggregated round file, and the round record lists every angle with its outcome and duration; the round document is retained even when the round ends in a hold or without a verdict. The formal review is never fanned out: one exhaustive pass per decision. Reason: native reviewers cap findings per pass (Codex `/review` reports 1-3 by design, openai/codex#4710, #5547), so breadth per decision replaces repeated decisions. Citation rule, enforced in code where the verdict is classified: a block reason must carry an axis tag (`[spec]` or `[standards]`) and a diff location (`@ file[:line]`); anything else is advisory, retained in the verdict file and the journal, and never blocks. Recommended split: R2 as three contract-bound angles (`ac-coverage`, `spec-deviations`, `edge-cases`) and R3 as one exhaustive pass, since a union of three broad reviewers multiplies uncited findings. A deterministic scope gate runs before any model call: changed paths outside `allow_paths` block the round (R2) or refuse the dispatch (R3) with no tokens spent. A renamed file is a changed path at its source and at its destination, so a rename from inside `allow_paths` to a path outside it, or from outside into it, is refused, and every R2 and R3 prompt lists both paths of a rename among the changed paths (card T1-RENAME-PATHS).

### Findings and dispositions

Every cited reason of a block (R2 round or R3 decision, by command or by the ship path; the root list and both axes of the verdict document; an advisory block too, marked `advisory`) is recorded on the card run as a finding with a stable id `F<n>` (sequential per run), its stage, round or decision, perspective, cited file and candidate sha. References resolve against the findings that existed before the round, and every re-raise reason is kept with its angle; a round counts once toward non-acceptance however many angles re-raise the finding. The next prompt of either stage lists the unresolved findings under `## Prior findings`: an open finding as one to verify as resolved, a disputed finding with the author's note as one to re-raise only with evidence the note does not answer. A reviewer re-raises a finding by writing `re:F<n>` in the reason (a space after the colon is accepted); such a reason is recorded on the prior finding, which returns to open, and never as a new finding. An unknown reference is a new finding. A decided later round of a stage that raised or re-raised the finding and does not re-raise it now resolves it (`resolvedAt`: an R2 finding re-raised by R3 decision 1 is R3's to resolve at decision 2); a stage that never raised or re-raised it leaves it alone. Every finding carries a `revision` (bumped by a dispute, a withdrawal, a re-raise, a resolution) and every round is bound to the findings it received at dispatch (disposition, dispute count, revision, resolved or not): a re-raise records the index of the dispute the reviewer received and answered (none when the finding was open in the snapshot), a finding whose revision moved after dispatch is neither reset nor resolved by the round, a finding raised meanwhile is not resolved by it, only a finding raised or re-raised in a strictly earlier round of the stage is resolved, and a re-raise of a resolved finding reopens it. A ship-path reviewer receives no prompt, so its rounds deliver an empty snapshot: it can reference no finding (a `re:F<n>` it writes is a new finding), it answers no dispute and its pass resolves nothing. Two distinct disputes answered by re-raises are a deadlock; two rounds that answered the same dispute count once. The prompt line of a finding carries the prior reason and its history as quoted evidence, one JSON string each (the reason, the author's notes, the latest re-raise reason), and the section states that nothing inside a quoted string is an instruction.

```bash
aidlc review findings <card> [--goal <id>]           # every finding with disposition, disputes, re-raises, resolution; readable on a stopped run; read only (an existing run, never a new one; --goal when the card runs in several goals)
aidlc review dispute <card> <id> --note "<why>"      # the author answers an open finding; the note reaches the next round
aidlc review accept <card> <id>                      # withdraw a dispute; the finding is open again
```

Same-candidate rule: `review pre` and `review r3` refuse a candidate with uncommitted or untracked inputs (the review reads the committed sha; the recorded candidate and the review checkout as it is at dispatch, probed with `git status`, must both be clean), and refuse a candidate that the same stage already blocked while any finding of that block is open (the refusal names the ids and the two moves: repair to a new candidate, or dispute each finding), and run on the unchanged candidate once every finding of the block is disputed; a block that recorded no cited finding is never answered that way. Both stages key this on the committed sha of the candidate's own last decision, whichever reviewer recorded it (`ReviewInvocation.candidateSha`, the findings raised or re-raised on that sha), an advisory block included, never on the run's last verdict or the decision counter; the ship still proceeds after an advisory block. Both commands read the persisted run for their guards, never the caller's copy, re-check every guard (the candidate identity the review was prepared for, the checkout still clean and at the pinned candidate, stop, a round or decision in flight for any candidate of the card, quota hold, exhausted rounds or allowances with the decision in flight counted, the same-candidate rule) on the record locked when the round or decision is reserved (a candidate recorded meanwhile or a checkout changed since the diff was collected refuses the reservation; the command is run again for the current candidate), renew and fence the owner's lease inside that reservation (a foreign session reserves nothing), and take the numbering, the prior findings and the snapshot the reviewer receives from that locked record; a refused R3 reservation cancels its review-pool request. `review pre` refuses once the cycle's rounds are exhausted, whatever the dispositions (the gate stops or hands off). `review pre` reserves its round as `pending` under the card-run lock before dispatch (one round in flight per card, whatever the candidate: a second dispatch is refused and `aidlc card next` waits on it; the round numbering counts the round in flight); a round with no result after the reviewer timeout plus the five-minute grace is dropped as abandoned by the gate, decided on the locked record (a round decided meanwhile stays and drives the gate; only an actual drop is journaled), and a result that arrives for an abandoned reservation is kept as evidence only (`discarded: reservation abandoned meanwhile`), never resurrected. `aidlc card next` follows the same rule: a pending block with open findings returns the repair directive naming them; with every finding disputed the SHIP gate issues the next round or decision on the unchanged candidate, reusing the DoD receipt the block cleared (`CardRun.blockedReceipt`, bound to the candidate digest) so no further attempt is recorded for an unchanged candidate; the same reuse lets exhausted R2 rounds decide at once. Disputes reach a reviewer only through the command path: with `formalReview.command` empty the ship-path reviewer re-reads a verdict file, so a disputed formal block stays pending until the candidate changes and the dispute is recorded for the human adjudicator. A pre-review pass stays valid for the candidate it reviewed in any later cycle, so a disputed R3 block on an unchanged candidate goes straight to decision two. Every card-run write goes through the card-run lock (`GoalStore.updateCardRun`, also behind `saveCardRun`: an exclusive `.lock` file next to the record naming its process, a 2 s wait with the deadline checked before every retry acquisition, so a wait that overran it never runs on a lock freed meanwhile, a 30 s stale age after which a lock is taken over only when its owner process is gone (a live owner keeps it however old), a takeover serialized by a second exclusive marker so a live lock is never removed, a stat or read failure other than a vanished file propagated (a lock this process cannot read is never taken over or released), and an ownership-checked write and release, so a writer whose lock changed hands during a long suspension refuses instead of writing over the new owner). Dispositions read the record inside the lock (a stop saved meanwhile refuses, the lease is fenced) and write back only the changed finding; a review completion commits from the locked record in a fixed order: a run stopped meanwhile keeps the result as evidence only and releases the reservation (no finding is recorded); a reservation the gate abandoned meanwhile is never resurrected; the owner's lease is renewed and fenced before anything is written (a review can outlast the 10-minute lease; a lost lease releases the reservation and stops the run); the findings, and for R3 the counters and the action (`recordReviewOutcome`), are computed from that record, so a decision another completion recorded meanwhile is counted, never overwritten; a result for a candidate the author replaced meanwhile (a new attempt recorded during the review) is recorded as history for its own sha without touching the newer candidate's receipts, effort or state. A ship-path decision records its invocation, counters and findings in one locked update, so a failure right after it leaves a consistent ledger and a replay of the same artifact records nothing twice; the ship outcome is then applied to the record locked at that moment (candidate and stop re-validated under the lock; the patch of each outcome, the review-fix or stop action, the retained receipt and the effort are computed from that record, so a decision or a failed check recorded meanwhile is kept and counted), and when the candidate changed or the run was stopped while the ship was in flight the outcome is history for the shipped candidate (decision, findings, evidence, operation result, a merge left as an unresolved operation) and the run is left where the newer candidate or the stop put it. Every other write (`saveCardRun`, the controller's included) is a compare-and-set on the run revision (`CardRun.revision`, bumped by every write under the lock; runs written before the field read at 0): a snapshot that does not carry the persisted revision was read before another write landed and is refused whatever it changes (a candidate, a receipt, a stop, a ledger entry), with the ledger entry named when the ledgers can (a missing round, decision or hand-off, a decided entry still held as pending, a released reservation still held, a regressed counter); the command is run again on the current record; findings are merged by revision; the paths that remove an entry on purpose (a released reservation, an abandoned round) write from the locked record. A `re:F<n>` reference resolves against the findings the reviewer received: an id added while the round was in flight is unknown to it and makes a new finding. A routed skip decides nothing about the findings; a ship-path verdict file re-read for the same candidate (a CI retry re-reading an unchanged advisory verdict) is the same decision and records nothing. The DoD receipt a block cleared is reused only once (consumed on restoration) and dropped by any later check failure: a failed attempt or lost checks clear the active receipt and the retained one (a success that reports lost checks is refused as contradictory), a red ship gate clears both too. When the SHIP gate reloads the run from the locked record (a dropped round, a recorded hand-off), a stop recorded meanwhile ends the call and a candidate no longer ready sends the caller back to `card next`, before any external effect; and right before the ship is dispatched the record is re-read under the card-run lock: the candidate the gate admitted must still be the record's, with its receipts, no stop, no round or decision reserved meanwhile, the same owner generation, the same review ledger counters, and the pre-review eligibility and the formal admission recomputed on the reloaded record (a decision recorded meanwhile moves the cycle, and a candidate admitted on the exhausted hand-off of the previous cycle holds no round in the new one), otherwise the operation intent and the pool request are cancelled, each step on its own so a failing ledger never skips the pool cancellation nor hides the drift, and nothing is dispatched (`wait` on `record-changed`, then `card next`); when that re-read cannot take the lock the intent and the pool admission are cancelled too and the error is the caller's. After the gate's own reload of the run (a dropped round, a recorded hand-off) a stop, a candidate or a review cycle that moved on sends the caller back to `card next` before any gate decision. The transient-CI rerun is decided on the CI ledger locked at completion, the grant, the denial and the directive alike: a rerun another window persisted meanwhile is kept and counted, one it cancelled meanwhile no longer consumes the allowance, and a denial is never computed from the snapshot the ship was issued from. A review panel settles every angle before it fails the round (a prompt that cannot be built, a retention failure), so no reviewer of the round is running when its reservation is dropped. A dispute needs a note; one dispute per re-raise that received the previous one, a withdrawn one included, so a second dispute of the same finding needs a re-raise recorded since the latest dispute from a round that received every dispute so far (`sawDisputes` on the re-raise; a round dispatched before the dispute received none of it and opens no second dispute, and a late one completing after an answering re-raise never revokes it); a finding re-raised after a dispute twice (two rounds of mutual non-acceptance) is a deadlock: a third dispute is refused, the STOP detail of the R3 second block or of exhausted R2 rounds names it, and with `preReview.onExhausted: "ship"` the residual handed to R3 names it in the journal (`PRE_REVIEW_DECIDED` with `exhausted`, `residualFindings` and `deadlock`, recorded once per cycle and candidate whether the SHIP gate or `review r3` reaches the hand-off first, `PreReviewLedger.handoffs`) and in the R3 prompt, where the finding's prior-findings line carries the deadlock marker. The human ruling path is the existing STOP/review hand-off. `PRE_REVIEW_DECIDED` and `REVIEW_DECIDED` carry the `findings`, `reraised` and `resolved` id lists (empty on the exhausted and discarded events, which add `residualFindings` for the hand-off); `FINDING_DISPUTED` and `FINDING_ACCEPTED` record the dispositions.

### Formal review (R3) as a command

The same mechanism runs the formal review when `formalReview.command` is set; otherwise the R3 verdict comes from the ship path (scaffold ReviewGate) as before. In this repository R3 is a headless Claude Opus 5.5 with no fallback (card T0-R3-OPUS-PRIMARY), limited to the Read, Grep and Glob tools, with no setting sources (no hooks or plugins) and no MCP servers (`--strict-mcp-config`, which also drops the account connectors); it receives the effort level `{effort}` expands to as `--effort <level>`:

```json
"gateRequired": true,
"formalReview": {
  "command": ["claude", "-p", "--model", "claude-opus-5-5", "--effort", "{effort}", "--tools", "Read,Grep,Glob", "--setting-sources=", "--strict-mcp-config", "--no-session-persistence"], "reviewer": "claude-opus-5-5", "timeoutMs": 1200000,
  "effort": { "default": "medium", "high": { "minChangedLines": 500, "paths": ["src/core/**", "src/coordination/**", "src/state/**"] } }
}
```

Codex `gpt-6-sol` was the primary, with Opus 5.5 as its fallback, until Codex became unavailable. No Codex fallback is configured: the fallback runs while the primary is held on quota, and a Codex run would fail as well. To restore Codex, put its command back as `formalReview.command` with `"reviewer": "codex"` and move the Opus 5.5 command to `formalReview.fallback`; Codex takes the level as `-c model_reasoning_effort=<level>`:

```json
"command": ["codex", "exec", "-m", "gpt-6-sol", "-c", "model_reasoning_effort={effort}", "--sandbox", "read-only", "--output-schema", "{schema}"], "reviewer": "codex"
```

Review effort (card T1-OPUS55-R3-3, superseding T1-OPUS55-R3 and T1-OPUS55-R3-2). `formalReview.effort` and `formalReview.fallback.effort` (optional) set the level `{effort}` expands to for that reviewer: `default` (`medium`, `high`, `xhigh` or `max`; `medium` when omitted; `low` is refused) and an optional `high` rule, `minChangedLines` (an integer from 0) and `paths` (globs matched like `allow_paths`); a `high` rule with a default of `xhigh` or `max` is refused, since it would lower the level. A dispatch runs at `high` when the candidate's added plus deleted lines reach `minChangedLines` or a changed path matches `paths`, and at `default` otherwise; without an `effort` object the level is `medium` (`src/core/review-effort.ts`). The lines are counted from the pinned `--text` diff collected for the review (`git diff --text <base>...<candidateSha> --no-color --no-ext-diff --no-textconv`: the `+` and `-` lines inside its hunks, so a file git treats as binary counts the hunks shown, a moved HEAD changes nothing, and no colour setting, external diff driver or `textconv` filter changes the text). A reviewer whose argv has no `{instructions}` receives that text in its prompt; a reviewer whose argv carries `{instructions}` receives a diff command to run instead, not the counted text. A non-empty collected diff with no `diff --git ` section is never read as zero lines: it selects `high`, or the policy default when that is higher, so a decorated diff never lowers the level. The path rule matches the changed paths the scope gate uses, `git diff --name-only -z <base>...<candidateSha> --no-renames`, which name a renamed file by its source and its destination, each as written and never C-quoted, so moving a file out of `src/core` counts as touching it and a non-ASCII name matches a single-segment glob such as `src/core/*.ts` (card T1-RENAME-PATHS). The level is chosen with the dispatched reviewer's own policy, the fallback's when the fallback runs, before the reservation, so a retry of the same candidate on the same reviewer runs at the same level. The invocation record carries `effort` only when the reviewer's argv carries `{effort}`; an argv without it is passed unchanged and records none. The level is placed wherever `{effort}` appears in an argument, so a reviewer that takes it inside a longer argument (Codex `model_reasoning_effort={effort}`) needs no code change.

Fallback reviewer (card T0-R3-FALLBACK-2). `formalReview.fallback` (optional: `command`, non-empty with no empty argument, since a reviewer runs through a shell on Windows and the shell drops an empty argument (write `--flag=`), and a `reviewer` that is not blank and differs from the primary's after trimming and case folding, as request keys and pool files fold them, required; `timeoutMs`, `shell` and `maxDiffBytes` defaulted as for the primary) names a second formal reviewer. The reviewer is resolved per dispatch from the card's ledger: the primary unless its latest invocation of the card, on any candidate, holds an unexpired quota hold (a quota belongs to the reviewer, so a candidate repaired after a fallback block goes to the fallback too), then the fallback unless it holds one too; with both held, `card next` is `wait` on `review-quota` until the earlier hold clears, and the reviewer whose hold cleared runs next. The fallback never replaces a primary that is not on hold, and a no-verdict or a block never switches reviewer. `card next` names the resolved reviewer in the review directive; `review r3` dispatches it and re-checks it on the record locked at reservation (a hold recorded or cleared meanwhile refuses: run the command again). Both reviewers share one ledger: the two-decision allowance, the single no-verdict retry and the same-candidate rule count decisions by either, so switching reviewer never adds a decision. The invocation, `REVIEW_DECIDED`, the evidence note, the canonical `.review/<card>.json` and the `review r3` summary name the reviewer that ran; a ship-path re-read of a fallback decision is the same artifact, not a second decision. With a fallback configured each formal reviewer queues in its own review pool, `<reviewPool>/<reviewer>`, because a quota hold resets the whole pool it lands in and the two reviewers hold separate quotas; the ship's own admission stays in the goal's pool. A request already stored under the same key (same candidate, base, policy and reviewer) keeps the pool it was enqueued in, so adding or removing the fallback never strands it; a refusal names the pool (`aidlc review status --pool <pool>`). Once one reviewer's dispatch is reserved for a candidate, the other reviewer's queued or held request for that candidate is cancelled when the card is its only requester (the pool's reset time is kept; a `NOTE` names the key; best-effort: a failure is journaled as `reviewRequestCancelFailed` and never fails the reserved review), since the card will not run it again unless its hold passes and another card's review would otherwise admit it and hold the slot with no one to run it. Without a fallback every behaviour, the pool and the candidate-scoped hold included, is unchanged. A diff above the fallback's own `maxDiffBytes` is refused naming `formalReview.fallback.maxDiffBytes`.

End-of-turn rule (card T1-OPUS55-PROMPTS): every review prompt and the reviewer agent say that the reply ends with the verdict JSON line and that a progress note, a summary that announces a next step or an offer to continue is not the end of the review; a headless reviewer whose reply ends on such a note with no verdict line before it has returned no verdict, which spends a no-verdict retry. Every review prompt says that a note after the verdict line is ignored only when it contains no JSON, since the reader takes the last JSON document that parses: a JSON document in the note is read instead of the verdict, and one that does not parse leaves no verdict (card T1-PROMPT-CHECK-2). The R2 prompt also asks for every finding the reviewer can defend: its block rule decides only whether a finding blocks, not whether it is reported.

Placeholders in argv: `{instructions}` (the prompt; when absent the prompt goes to stdin, which avoids shell quoting of a multi-line prompt on Windows), `{base}`, `{head}`, `{card}`, `{schema}` (a materialised `verdict.schema.json` for reviewers that enforce structured output), `{cwd}`, `{effort}` (the level chosen for the candidate, see Review effort). `aidlc review r3 <card>` refuses to run before the pre-review pass when R2 is configured, runs the command with a receipt, writes the candidate-bound verdict to `.review/<card>.json` (the file the ship paths read; a ship path re-reading a pass is not a second decision) and records the decision through the existing R3 ledger: two substantive decisions, one no-verdict retry, quota hold as WAIT with `holdUntil`, second substantive block as STOP/review. Guards: a further required review beyond the two decisions is STOP/review before any third run; an advisory block (standards-only without a required gate) is recorded and the ship proceeds with the findings retained; a verdict naming another sha is stale, never a pass, and never overwrites the candidate-bound file; `review pre` and `review r3` refuse to run inside an active quota hold, on a stopped card run, or when the checkout HEAD is not the pinned candidate; `review r3` also refuses while a formal review of the card is in flight (any candidate), when the shared review pool does not admit it, and once the two-decision allowance is used, a decision in flight counted, even if the candidate already holds its pass. The invocation is reserved in the ledger before dispatch (what the reviewer receives is retained next to its verdict as `.review/<stem>.reservation.json`) and the decision is committed from the record locked at completion, so a concurrent call cannot spend the same decision, a STOP saved meanwhile is kept, and a decision recorded meanwhile is counted (two blocks stop the card whichever completed first). The complete result is published atomically next to its verdict (`.review/<stem>.result.json`: outcome, status, reasons, retry-after, the pool request key and the queue sequence it was admitted under, the snapshot the reviewer received) before the pool request is settled and the decision committed. A later step that did not land (the card-run lock held by another writer, the queue store unavailable) keeps the reservation: the next `review r3` settles the pool request the envelope names (its key and queue sequence: a request under the same reusable key with another sequence belongs to a later attempt of the candidate and is left alone; a `retry-after` request whose slot release or pool deadline did not land is held again with its own deadline) and commits the result under the same invocation without running the reviewer again, a hold as a hold with the deadline the envelope recorded, a no-verdict as a no-verdict (a spawn failure is one), and a result for a candidate the author replaced meanwhile as history for its own sha; only an envelope bound to the reservation (its invocation id, candidate digest and pinned sha), complete (the pool request key, the snapshot) and consistent (an outcome and a run status of their enums that agree: a decision ran to success, a no-verdict or a hold did not) counts, and it carries the verdict it was classified from, so the recovery classifies from the envelope alone and never reads the sidecar; a decided envelope without its verdict, one with a verdict that disagrees with its outcome, or a no-verdict or hold envelope that carries a verdict, is an inconsistent artifact and recovers nothing. The recovery runs before every guard of a new dispatch, so a run stopped meanwhile still commits the retained result, as evidence only (the reservation released, the pool request settled, no decision counted), before the command reports the stop. Without an envelope the reservation is a review still finishing until it is older than the reviewer timeout and the grace (from the log when one exists, from the request otherwise), then an unrecoverable result charged against the no-verdict allowance with its pool request settled under the key of the reservation's own base, policy version and reviewer, never the configuration current at recovery time; a retention failure after the reviewer returned is charged the same way (the reviewer ran); a dispatch that fails before any receipt retains the failure as `.review/<stem>.failed.json` (best-effort, like the release and the pool cancellation: none of them masks the dispatch's own error), names that request in the marker (key and queue sequence), cancels it, and only then releases the reservation; a cancellation that fails keeps the reservation and its marker, and the next `review r3` cancels the request from the marker before it releases the reservation and dispatches, so the request of a reviewer that never ran is never joined as a running review; a release removes only a reservation still pending on the locked record (a decision another window recovered under the invocation keeps its counters) and journals only what it released; an R2 round whose dispatch failed the same way carries the same marker and is dropped by the next gate pass at once, not after the timeout. A completion of an invocation already decided by another completion removes only a pending reservation, never the decision. The canonical `.review/<card>.json` is published atomically, naming the decision it publishes (`invocationId`), only for a successful, non-stale decision committed on the current candidate; `REVIEW_DECIDED` is journaled whether or not that publication landed (`canonicalPublished`, `publicationError`), and the SHIP gate repairs the document before the ship, for a pass and an advisory block alike, when it is missing, names another sha or still carries an earlier decision on the same sha (the block a disputed re-review then passed): rebuilt from the committed envelope bound to the invocation and agreeing with its outcome (a sidecar only for a decision from before envelopes existed, and only when it agrees), published with the recorded classification and journaled as a `NOTE` per repair; an advisory block is published as a pass with the findings under `advisory`. A document that reports its own failure keeps it. Dynamic instructions never pass through a shell; perspective names must be filename-safe and unique. With `gateRequired: true` every block is merge-blocking: the card returns to REVIEW_FIX, the episode reopens without spending an attempt (the two decisions are the formal review's own budget), and the repaired candidate restarts the pre-review cycle (R2 round 1) before `review r3` runs again; an unchanged candidate whose findings are all disputed keeps its pass and goes to decision two. `aidlc card next` in SHIP returns `pre-review`, then `review`, then ships. Decision two receives the delta since the candidate decision one reviewed; the reservation file and the result envelope carry the policy hash and the delta paths, so a decision committed from the retained envelope records the same hash and marks first-round misses the same way; the reserved hash is authoritative: an envelope naming another policy hash is not the reservation's and recovers nothing, one naming none recovers under the reserved hash and marks nothing.

### Review statistics

`summarizeReviews` (`src/review/stats.ts`) reads the two review ledgers of every card run and the `superseded_by` chain of the card registry, and reports per card: `r2` (`rounds`, decided rounds only, a round still reserved for a dispatch in flight is not one; `blocks`; `noVerdict`; `quotaHolds`; `durationMs`, the sum of the measured round durations; `blocksByPerspective`, the blocking panel angles by name, a blocked round with no panel record counted under the reviewer that decided it), `r3` (`decisions` and `blocks`, the ledger's own substantive counters, so a no-verdict and a quota hold are neither; `durationMs`, the sum of request to decision over the invocations whose decision artifact the run's evidence carries, `r3-<stem>` for invocation `r3:<stem>`, and nothing for a decision still in flight), `findings` (`total`, `pre`, `formal`, then `open`, `disputed` and `resolved`, which partition the total the way `aidlc review findings` prints each finding, plus `reraised`, the findings a later round raised again, and `firstRoundMiss`, the findings marked `outsideDelta`), `coverage` (`roundsRequested`, the decided rounds that retained a coverage record, so a round that asked for none is not one and a round still reserved is neither; `roundsComplete`, of those the rounds with no unaccounted, conflicted or inconsistent item and no malformed entry; `unaccounted`, `conflicted` and `inconsistent`, the item counts summed over the rounds; `r3SpecFindingsAfterIncomplete`, the formal findings whose reason carries the `[spec]` axis tag and whose `candidateSha` is one whose last decided R2 round reported an unaccounted item, so a later decided round on that candidate ends the question for it, whether it accounted for the items or asked for no coverage at all; rounds and findings are joined over every run of the card before they are matched, so a candidate reviewed under one goal and cited under another is read as one timeline, and the rounds are ordered by the decision each one landed (the artifact `wallMs` also measures to), then by the request, the cycle and round, the goal and the reservation, all compared by code unit, so a round held for admission and decided late is last however early it was requested and the order never depends on which runs the caller passed first or on the runtime locale; a round whose artifact the run did not retain is placed by its measured end, which cannot cover that wait, so it never settles a candidate another round states its decision for, and decides only where no round on the candidate carries one) and `wallMs`, from the first review request to the last pass, or to the last review when none passed, each review measured to the completion its artifact records (`pre-review-<cycle>-<round>-<attempt>` and `r3-<stem>`), so a round held for pool admission counts that wait; a round with no artifact falls back to the reviewer runtime after its request. A pass is a recorded pass of either stage: an advisory block opens the ship without being one, so a card whose last decision is an advisory block measures to its last pass, and to that block when nothing passed. A card run without reviews reports zeros. The numbers of a card cover every run of that card, so a card run under several goals is reported once, for all of them together, and `goalId` is reported only when one goal ran it. Where the chain names predecessors, the card also reports `family`: every predecessor with the same fields, oldest first, and the totals of the family with this card included (the wall times are added, not spanned); a predecessor with no run of its own counts as zeros, and a chain that loops is walked once.

```bash
aidlc review stats [--goal <id>] [--card <id>]   # JSON when stdout is not a TTY, one line per card otherwise
```

The command reads every goal's card runs and never writes. `--goal` narrows which cards are reported, never what the family is aggregated from, so a predecessor that ran under another goal keeps its own numbers instead of reading as zeros. `--card` reports that card alone, with the family it supersedes, and answers about it with zeros when it has no run. The line form prints one line per card, each family member under the card that supersedes it (`+`) and then the family total (`=`). Its coverage segment reads `coverage: <roundsComplete>/<roundsRequested> complete, unaccounted <n>, conflicted <n>, inconsistent <n>, r3 spec findings after incomplete <n>`, and `coverage: not requested` for a card no round of which carried a coverage record.

## Audit

```bash
aidlc evidence retain --goal <id> --id dod-T1-STATUS-API --kind dod-receipt --file out/test.log --candidate <digest>
aidlc audit seal --goal <id> --final-sha <sha> --final-digest <digest>
aidlc audit verify --goal <id> | --all
aidlc audit verify --goal <id> --claim-full [--capture-boundary]
```

`verify` reports the level (`none`, `recorded`, `traceable`, `independently-verified`) and findings: blocking `JOURNAL_CHAIN`, `OP_UNRESOLVED`, `OP_INTENT_MISSING`, `TRACE_MISSING`, `WORK_AFTER_TERMINAL`, `MANIFEST_SEAL`, `MANIFEST_STALE`, `ARTIFACT_MISSING`, `ARTIFACT_ALTERED`, `EVIDENCE_STALE_CANDIDATE`; warnings `OP_UNKNOWN`, `MANIFEST_UNSEALED`, `MANIFEST_TRAILING`. `WORK_AFTER_TERMINAL` counts a dispatch, an issued operation or an attempt only when the latest disposition journaled before it is terminal (`GOAL_DONE` or `GOAL_STOPPED`); a user-authorised re-admission ends that state: the `GOAL_TAKEOVER` of `aidlc goal resume`, which names the generation it links from and moves to a later one, or the `GOAL_STATE` from `STOP` to `CARDS` that `aidlc goal extend` writes in the stopped generation when it re-admits a time stop, so the continuation of a resumed or extended goal is not work after a terminal disposition (card T0-AUDIT-READMIT). A lease takeover (`aidlc goal takeover`) re-admits nothing, and work journaled by a generation below the highest one a resume moved to still blocks. Any block sets exit 1. `--claim-full` evaluates the "fully audited" claim: `verified` only at `independently-verified` with `--capture-boundary` asserted by the operator; otherwise `BLOCKED/capability` with the prerequisite. A mutation journaled after the seal makes it `MANIFEST_STALE`; non-mutating closure events after the seal are only `MANIFEST_TRAILING`. Seal after the last mutation.

## Ship gates (GitHub ship path)

`github.requiredChecks` lists the check-run names that must be present and conclude success on the candidate before the squash merge (skipped or neutral never satisfies a required name). A required name absent from the check runs of the head counts as pending until `github.ciTimeoutMs` (default 30 minutes, polled every `github.ciPollMs`, default 20 seconds), never as satisfied; every other check that reports on the head must succeed as well. `github.requireVerdict` (default true) keeps the candidate-bound R3 verdict a precondition of any remote effect; it may be false only while `gateRequired` is false (the config parser refuses the pair), and a block verdict present for the candidate fails the ship in either case. This repository requires `check (ubuntu-latest, 22)`, `check (windows-latest, 22)`, `build-test` and `Gitleaks (committed history)`; `evals` runs only for some paths and stays out of the list, and it still blocks when it reports red.

The gitleaks history scan (`security-scanners.yml`) is a blocking job. A red check run whose name matches a secret or security scan (gitleaks, secret scan in any spelling, security), or raw gitleaks output given to `aidlc ci classify --log`, is the CI class `security`: it is never rerun, the card stops with reason `risk`, and the way out is to remove the finding from the change or the history and ship a new candidate. The ship path reports its check runs on the gate lines as JSON with bracket-encoded names, and the runner classifies a red gate from those checks alone: a check name is never evidence of a transient or code failure, a green scan next to a red build is a code defect, every red gate line counts, plain name=conclusion pairs are still read, and a red pair-like line that cannot be parsed and names a scan fails closed as security.

Base sync (cards T0-SHIP-BASE-SYNC and T0-SHIP-BASE-SYNC-2): after the verdict check and the read-only PR reconciliation (a merged PR for the branch ends the ship as `merged` before any sync, so a retried squash-merged candidate never starts a merge; an open PR is reused after the push) and before any push, PR or local merge, the path fetches the base (remote mode; local mode first checks that the main checkout has `refs/heads/<base>` checked out by its full symbolic ref, failing before any sync or merge when another branch or a detached HEAD is there, then uses the local branch) and tests the merge with `git merge-tree --write-tree HEAD <ref>`, which needs git 2.38 or newer and touches neither a ref nor the worktree. A clean test logs one line and ships the reviewed head unchanged. A conflict starts the same merge in the card worktree without committing, so the conflict markers are there for the `merge-conflicts` skill, and, once `MERGE_HEAD` proves the merge is in progress (any other outcome of that merge is `[SHIP-BASE-SYNC-FAIL]` with the output flattened on one line: a filename such as `CONFLICT (content).txt` in an operational error is never a diagnostic), prints git's own lines (`CONFLICT (content): Merge conflict in <path>`, `Automatic merge failed; fix conflicts and then commit the result.`; brackets and percent signs in a path are encoded as in the gate lines, so a path never forms a sentinel or a resume marker; every failure detail of the path, verdict reasons and command output included, is flattened and encoded exactly once the same way, the CI gate lines excepted; the resume command and PR number come from the path's own state) on the ship output, and fails with `[SHIP-BASE-SYNC-CONFLICT]`: the runner returns the card to BUILD naming `merge-conflicts` with the DoD receipt cleared and the repair persisted, and the resolved merge commit is a new candidate (DoD, R2 and R3 run again). Before this sync a branch that conflicted with its base became a PR GitHub ran no `pull_request` workflow on, and the CI gate timed out after `ciTimeoutMs` into STOP/ci (PR #15). A failed fetch, an unresolvable base, a merge-tree error (an older git prints `unknown option`) or a merge that completes although merge-tree reported a conflict (aborted, head unchanged; when the abort itself fails the line says the index and worktree still carry the merge and names `git merge --abort` as the manual step) is `[SHIP-BASE-SYNC-FAIL]` with git's stderr on the line: STOP/tool with the `[SAGA-RESUME]` command and nothing pushed. The base name is normalised once (`origin/` stripped once) and names the PR target, the fetch refspec and the tested ref alike. When the only unmerged path of a base-sync conflict is `CHANGELOG.md`, the path rewrites it with `git checkout --conflict=diff3` and resolves it only when every hunk lies in `## Unreleased`, has an empty base part (both sides only added lines there) and adds no `## ` heading: each hunk keeps the card's lines, then the base's, the merge is committed, and the ship ends with `[SHIP-BASE-SYNC-MERGED]` naming the merge commit, pushing and merging nothing (card T0-BASE-SYNC-CHANGELOG-2). Any other conflict, another path, a hunk outside `## Unreleased`, a hunk with a base part or one that adds a heading, is left whole for the merge-conflicts skill. The merge is a new candidate either way: the runner opens the merge-conflict repair with the DoD and retained receipts cleared, so the DoD, R2 and R3 run on the merge and nothing reviewed on the candidate it replaces carries over.

## Companion skills

Advisory skills installed next to `aidlc-loop`; the loop's gates decide, and a skill never overrides `aidlc next`. Each is read by path when the step needs it (the implementer, investigator and planner agents point at them) or called by name in a session.

| Skill | When the loop reaches for it | What it must not do |
|---|---|---|
| `tdd` | BUILD, before writing or changing a test: the agreed seams are the acceptance items and the interfaces they exercise; anti-patterns that fake a RED (implementation-coupled, tautological, horizontal slicing); mocks only at system boundaries | Add a test at a seam the card does not name; weaken a test |
| `diagnose` | T0-bugfix and the card `diagnosis:` field, or a DoD/CI failure with no known cause: a red-capable command first, then 3-5 ranked falsifiable hypotheses, one variable per probe, the regression test before the fix | Form a hypothesis before the red-capable command exists; count attempts (that stays with `aidlc card attempt`) |
| `grilling` | T1/T2 intake while the intent's Open questions are not empty, and the T2 plan checkpoint: rounds over the frontier, recommended answer first, at most three rounds, leftovers become `[TBD: ...]` in the spec | Grill on T0 work; ask for a fact that can be looked up; add a confirmation gate the loop does not have |
| `merge-conflicts` | SHIP when the base moved and the merge-based sync stops on conflicts: resolve by the intent of each side, merge only, rerun DoD and review | Rebase or amend receipt-bound history; take a whole side blindly |

Lessons: `docs/LESSONS.md` is append-only. PREPARE reads it once per card; CLOSE appends at most one dated `NEVER|ALWAYS|NOTE` line when a review block or an incident taught a rule the playbook did not state.

## Upgrading a downstream repository

`aidlc init` adds files that are missing and never overwrites an existing one, so a re-run on an existing repository installs new skills, agents, docs and workflows and leaves everything else as it is. `--force` overwrites ordinary files (including `aidlc.config.json` and `docs/LESSONS.md`) but never refreshes a CLAUDE.md section that is already present. To take a new `REVIEW.md` or CLAUDE.md section into an existing repository, copy the changed sections by hand and bump `reviewPolicyVersion` in `aidlc.config.json`: the version is part of the review admission key, so a pass already recorded for a candidate stays valid and only a changed candidate is reviewed under the new text.
